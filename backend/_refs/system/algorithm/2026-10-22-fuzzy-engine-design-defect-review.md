## 0.5 第二轮修正：档位问题的定性（重要）

用户判断：

> 原先确实是模糊等级默认为 3，但上次讨论我们以 5 为基础进行了调整。虽然说原有的 3 层规则不满足现有的 5 层，但是我觉得这应该不是主要问题，**算法不会因为 3/5 级模糊等级就不能用，这肯定是算法设计的问题**。

**该判断成立。本文 §1.2 的原措辞「5 档规则不满足 3 档规则」有误导，在此更正：**

规则串 `X_low` 本身**没有**随档位数改变，改变的是**引擎解释它的方式**。规则库一个字都不用改。真正的问题是：引擎把「档位词 → 桶索引」这一步写成了全局静态表。

第二轮新增 2 个可复跑脚本 + 3 项实证：

| 脚本 | 层次 | 回答什么问题 |
|------|------|-------------|
| `_dev_refs/diag_fuzzy_level_design.py` | 纯算法层 | 三种修法（维持全局表 / 改全局表 / per-parameter）各自的后果 |
| `_dev_refs/diag_fuzzy_level_audit.py` | 真实 DB 全库体检 | 词表三方分叉 + 规则库与各参数档位数的兼容性 |

核心结论三条：

1. **把全局表改成 5 档语义 = 用一个 bug 换另一个 bug**（§1.2.2）
2. **规则库侧零缺陷** —— 用最长后缀匹配还原「真参数名 + 档位词」后，3440 个可判级前件**全部与所属参数的档位数兼容**（§1.2.3）
3. **病根不是「不支持 5 档」，而是「整条链上只有一处是全局的」**（§1.2.1）

## 1. 五层设计缺陷

### 1.1 词法层：档位词空间坍缩（`split_phase`）

`split_phase` 情形 3「从右往左找第一个 level 词，前面的全部归入 name」：

```
IV0_low          -> {'name': 'IV0',          'level': 'low'}
IV0_very_low     -> {'name': 'IV0_very',     'level': 'low'}     ← 参数名被污染
IV0_extremely_low-> {'name': 'IV0_extremely','level': 'low'}     ← 同上
IV0_level3       -> {'name': 'IV0',          'level': 'level3'}  ← 这条是对的
```

**后果链**：`IV0_very` 查不到 RuleKeyword → 前件被跳过 → `connected_matrix` 该行全 0 → `conditions.size == 0` → 激活度恒 0 → **整条规则静默失活**（不是报错，是无声消失）。

**影响面**：当前 1643 条活跃规则里 **0 条**用到 `very_*` / `extremely_*` 前件，所以这是**前向风险**而非现存问题。但它意味着 5/7/9 档在规则串层面**无法被正确表达**——`IV0_very_low` 会被当成参数 `IV0_very` 的 `low` 档，与 `IV0_low` 混为一条。

**正确解法：最长后缀匹配**。把已知档位词按长度降序遍历，取能作为后缀匹配的最长那个：
`IV0_very_low` → 匹配 `very_low`（len 8）优先于 `low`（len 3）→ name=`IV0`, level=`very_low`。

（§1.2.3 已用这个方法验证：**全库 3440 个可判级前件在最长后缀匹配下零不兼容**，说明现存规则库本来就是干净的，E1 不会改变任何一条规则的解释结果。）

### 1.2 档位映射层：全局静态表 vs 每参数独立档数

`HS_MAPPING_DICT` 是**全局静态表**，语义固定为 3 档：

```
low→0, mid→1, medium→1, high→2
```

但桶数由**每个参数自己的** `RuleKeyword.fuzzy_level` 决定（3/5/7/9 皆可）。两者不可能对齐：

| fuzzy_level | 桶序（`FUZZY_LEVELS`） | 规则写 `X_low` 命中 | 规则写 `X_high` 命中 |
|---|---|---|---|
| 3 | low, mid, high | bucket 0 = low ✅ | bucket 2 = high ✅ |
| 5 | very_low, low, mid, high, very_high | bucket 0 = **very_low** ❌ | bucket 2 = **mid** ❌ |
| 7 / 9 | `FUZZY_LEVELS` 里根本没有 | 永远只落在最左 3 桶 | 同左 |

**影响面（真实 DB）**：**1643 条规则的结论参数，100% 是 `fuzzy_level=5`** → 档位错位一档影响面 = 100%。

实证（x=30，论域 [0,120]）：

```
fuzzy_level=5 的隶属度 = [0.1353, 1.0000, 0.1353, 0.0003, 0.0]
                          very_low  low    mid    high  very_high
规则 IV0_low  → bucket 0 → 0.1353（实为 very_low 桶）
规则 IV0_high → bucket 2 → 0.1353（实为 mid 桶）
```

两者完全对称 —— 规则写 `low` 和写 `high` 命中的是「very_low」和「mid」，**语义完全错位**。

#### 1.2.1 病根定位：整条链上只有一处是全局的

把「读懂一条规则」拆成三层，每层本该由谁决定：

| 层 | 内容 | 应由谁决定 | 现状 |
|---|---|---|---|
| 知识层 | 规则串 `X_low` 表示「X 低」 | 规则作者 | ✅ 正确 |
| **解释层** | **`low` 在 X 的档位词表里排第几 → 桶索引 k** | **X 自己的 `fuzzy_level`** | ❌ **全局静态表** |
| 推理层 | `μ_k(x) = gauss(x; mean[k], σ)` | X 的论域 + 档位数 | ✅ **已经是 per-parameter** |

**推理层本来就是对的**：`nets.py::FuzzyFeature` 构造高斯参数时
`sigmas = (hi - lo) / (2 * (f_level - 1))`、`means` 按 `f_level` 取分位点 —— 全部随参数变化。
**唯独「档位词 → 桶索引」这一步用了全局表。**

再看系统其他部分：

| 组件 | 是否 per-parameter | 位置 |
|---|---|---|
| 前端规则表单选词 | ✅ 是 | `RuleMethodForm.vue::levelOptionsFor()` → `LEVEL_WORDS[kw.fuzzy_level]` |
| 前端缺陷反馈选档 | ✅ 是 | `DefectFeedback.vue::getLevelOptions()` |
| 引擎的隶属度参数 | ✅ 是 | `nets.py::FuzzyFeature` |
| **引擎的档位→桶查表** | ❌ **否** | `nets.py` L270 / L280 / L633 → `HS_MAPPING_DICT[level]` |

> **这是「算法设计问题」的最硬证据：规则编写侧、推理侧都已经是 per-parameter，
> 整条链上只有「档位→桶」这一处是全局的，而它恰好是所有规则必经的咽喉。**
>
> 这不是设计选择，是**实现与设计意图不一致** —— 当初写引擎的人是知道档位该
> per-parameter 的（隶属度参数就是这么写的），只是查表那一步走了捷径。

#### 1.2.2 三种修法对照：改全局表是「用一个 bug 换另一个 bug」

`diag_fuzzy_level_design.py`：两个参数同一论域 `[0,100]`（KA=3 档、KB=5 档），
取 x=50（各自论域正中），看 `X_low` / `X_high` 命中哪个桶。

| 方案 | KA(3档) low | KA(3档) high | KB(5档) low | KB(5档) high |
|---|---|---|---|---|
| **A 维持全局表（现状）** | 桶0=low ✅ 0.1353 | 桶2=high ✅ 0.1353 | 桶0=**very_low** ❌ 0.0003 | 桶2=**mid** ❌ **1.0000** |
| **B 改全局表为 5 档语义** | 桶1=**mid** ❌ 1.0000 | 桶3=**越界** ❌ | 桶1=low ✅ 0.1353 | 桶3=high ✅ 0.1353 |
| **C per-parameter 词表** | 桶0=low ✅ 0.1353 | 桶2=high ✅ 0.1353 | 桶1=low ✅ 0.1353 | 桶3=high ✅ 0.1353 |

关键判据：**x 在论域正中时，low 与 high 的激活度应当对称且都偏低**（x 确实不在两端）。

- 现状下 KB 的 `X_high` = **1.0000** —— 规则写「高」时其实在判「x 处于中间」，
  **命中逻辑整体平移了一档**。
- 方案 B 把 3 档参数的 `high` 推到桶 3，而 3 档只有桶 0/1/2 → **桶越界**
  （生产代码里对应 `nets.py` 的 `logger.error('index ... is out of bounds')` 分支）。

**方案 C 是唯一正解**：档位→桶的映射随参数而变，而不是把某一张全局字典从 3 档改成 5 档。

#### 1.2.3 全库体检：规则库侧零缺陷

`diag_fuzzy_level_audit.py`（真实 DB，1643 条活跃规则，311 个 RuleKeyword）：

| 检查项 | 结果 |
|---|---|
| RuleKeyword.fuzzy_level 分布 | **5 档 310 个（99.7%）／3 档 1 个（0.3%）／7 档 0／9 档 0** |
| 前件参数的 fuzzy_level 分布 | 5 档 3435 次（100%） |
| 结论参数的 fuzzy_level 分布 | 5 档 1643 次（100%） |
| **前件档位词与所属参数档位数的兼容性** | **3440 个可判级前件，零不兼容** |
| 结论侧 | 数值结论 1544 条 / 档位结论 **0 条** / 提示文本结论 99 条 |

两条重要推论：

1. **规则库侧没有任何缺陷**。用**最长后缀匹配**（`IV0_very_low` → name=`IV0`, level=`very_low`，
   而非现状 `split_phase` 的 name=`IV0_very`）还原后，全库 3440 个前件全部与所属参数兼容。
   **⇒ 改引擎不会破坏任何一条现存规则。**
2. **Mamdani 层（`FuzzyRuleNet`）实际是死代码**。全库 **0 条**档位结论（`X_add_low` 这种），
   1643 条规则全是 TSK 数值结论。⇒ §1.2 讨论的档位语义，实际只影响 TSK 的**前件门控**，
   结论侧根本不走档位。

#### 1.2.4 三方词表分叉（另一个待补的洞）

| 来源 | 3 档 | 5 档 | 7 档 | 9 档 |
|---|---|---|---|---|
| 前端 `rule-const.ts::LEVEL_WORDS` | low/medium/high | very_low/low/medium/high/very_high | extremely_low/very_low/low/medium/high/very_high/extremely_high | **缺失** |
| 后端 `macros.py::FUZZY_LEVELS` | low/**mid**/high | very_low/low/**mid**/high/very_high | **缺失** | **缺失** |
| 引擎 `macros.py::HS_MAPPING_DICT` | low=0, mid/medium=1, high=2 | **缺失** | **缺失** | level1..level9 |

- 三处词表三套内容，**只有前端是 per-parameter 的**。
- 后端用 `mid`、前端用 `medium`（同义，历史兼容）—— 而 `HS_MAPPING_DICT` 里两者都指向 1。
- **9 档是空洞**：`RuleKeyword.FUZZY_LEVELS` 提供了 9 档选项，但前端 `LEVEL_WORDS` 没有 9 档
  → `levelOptionsFor()` 会兜底返回 **3 档**词表 → 运维一旦把某个参数改成 9 档，
  前端表单会静默给出错误的档位选项。
- `specs.py` L305-328 已经写明：「HS_MAPPING_DICT 缺 5/7 档是**规则库侧**的问题……属于算法内核改造范围」。
  → 这条注释的**定性需要更正**：不是规则库侧问题，是**引擎解释层**问题（规则库侧实测零缺陷）。

### 1.3 语义层：缺陷在整个推理中没有位置

三个叠加事实：

1. **缺陷前件被静默丢弃（恒真）**。`collect_param_names()` 剔除缺陷名 → 缺陷不在 `pre_dict` → `_construct_numtskruleNet` 里 `if not self.pre_dict.get(name): continue` → 跳过。
   实测：`IF ABERRATION_low AND IP0_low THEN IP0_add_2` 与 `IF IP0_low THEN IP0_add_2` 激活度**完全相同**（均 1.000000）。

   > **推论**：`AND` 语义里只剩参数条件，缺陷不提供任何权重。缺陷在整个模糊推理中**只起「选哪套规则」的作用**。

2. **只有缺陷前件的规则完全失活**。`IF SHORTSHOT_high THEN IP0_add_10` → 无门控 → 激活度恒 0 → 永不产出建议。

3. **缺陷档位只在路由层过滤，且可被绕过**。`RuleQueryService._match_defect_level` 在 `defect_level` 为空时 `return True` → low/medium/high **三套完全不同的调整方案**同时进数值层，直接相加：

   ```
   activation=0.333333  IF ABERRATION_low    AND IP0_low THEN IP0_add_1
   activation=0.333333  IF ABERRATION_medium AND IP0_low THEN IP0_add_5
   activation=0.333333  IF ABERRATION_high   AND IP0_low THEN IP0_add_10
   → 累加 delta = 5.333333
   ```

   > 缺陷档位本该是**选哪套方案**的开关（或强度系数），现在它只在一处生效且可被绕过。

**影响面（真实 DB，1643 条活跃规则）**：

```
前件个数：  1 个: 6 条    2 个: 1422 条   3 个: 125 条   4+: 90 条
有效门控数：  0 个: 136 条 (8.3%)    1 个: 1304 条 (79.4%)
             2 个: 130 条 (7.9%)    3 个+: 73 条 (4.4%)
```

**79.4% 的规则只剩 1 个门控** —— 意味着「多前件 AND」这个语义在绝大多数规则上根本不存在，prod 连接与 min 连接在这 92% 的规则上等价。

零门控的 136 条里：130 条是 `X_worse` 前件（`CLAMP_worse` / `IPOS_worse` / `NT_worse`）+ 结论是 `X_adjust_提示语`（走 check 分支，仍能出文本建议）；6 条是「只有缺陷名」。

### 1.4 聚合层：两件不同的事被乘在一起（最致命）

现状的输出公式（`fuzzy_algorithm._infer_numeric_layer`）：

```
delta_p = Σ_i ( 调整量_i  ×  (激活度_i / Σ_全部规则激活度)  ×  priority_i )
                   ^^^^^^     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^^
                  工艺知识      相对适用强度（跨参数共享分母）    规则权威度
```

三个语义问题：

1. **调整量（绝对工艺知识）被乘上相对强度**。规则写「注射压力加 2 MPa」是领域知识，不该随同批次命中了多少条别的规则而缩放。
2. **归一化分母跨参数共享**。IP0 的规则和 MBP0 的规则抢同一个分母 → 命中别的参数就摊薄 IP0。
3. **priority 不参与归一化**。`new_activations * priority_array` 在归一化**之后**相乘，权重和 ≠ 1 → delta 总量随 priority 的绝对尺度漂移。

**实证 A（构造数据，9 条规则）**：

```
规则写的调整量: IP0_add_2  → 期望 +2.0
实际推出: IP0 = 0.222222      被摊薄 9.0×
对照组（只有 IP0 一条规则）: IP0 = 2.000000  ← 等于规则写的值
```

**实证 B（真实 DB，defect=ABERRATION / level=low，命中 12 条）**：

| 参数 | 规则写的调整量 | 现状推出 | 倍数 |
|---|---|---|---|
| CT | −2.00 | **−0.0021** | 0.001 |
| IP0 | +2.00 | **+0.0063** | 0.003 |
| MSR0 | −2.00 | **−0.4949** | 0.247 |

### 1.5 论域层：「低/高」的基准从来没有被定义

`RuleKeyword.range_min/max` 的**模型注释自己写着**：

> 取值范围是通用默认值/模拟推荐值，非设备物理极限
> 实际推理时：设备真实范围 > RuleKeyword 默认值

但引擎一直直接用它当论域（`RuleKeywordAdapter` → `FuzzyFeature`）。

**真实数据体检**：

| 参数 | fuzzy_lvl | range_min | range_max | 真实值 | 相对位置 | 判定 |
|---|---|---|---|---|---|---|
| BT | 5 | 0 | 50 | 250 | 500% | **论域外** |
| NT | 5 | 0 | 50 | 250 | 500% | **论域外** |
| MBP0 | 5 | 10 | 50 | 4.7 | −13% | **论域外** |
| CT | 5 | 0 | 120 | 5 | 4% | |
| IP0 | 5 | 0 | 200 | 84 | 42% | |
| IV0 | 5 | 0 | 120 | 30 | 25% | |
| MSR0 | 5 | 0 | 200 | 60 | 30% | |

**3/7 参数论域失真。**

更深一层的问题：规则库本来按 `polymer × product` 分库（`RuleMethod.polymer_abbreviation` / `product_category`），**分库只解决了「规则集合不同」，没解决「低/高的标准不同」**。同一个 `IV0=30 mm/s`，在「包装」和「汽车内饰件」上得到同一判定——而业务上这两者的「注射速度偏低」显然不是一回事。

## 2. 关于「矩阵运算识别规则」这个判断

**矩阵没有识别任何东西。** `connected_matrix` 是一张 one-hot 门控表：

- 行 = 规则，列 = (参数, 档位) 组合，命中置 1
- 唯一作用是 `connected_matrix * membership_degrees` 的广播乘，然后取 min / prod

它带来的实际成本：

| 成本 | 证据 |
|---|---|
| index 偏移双份维护 | `pre_dict` / `sol_dict` 各一套 `index` 累加 |
| 行下标与矩阵行错位 | 代码里留着 `if row_idx < len(self.connected_matrix)` 防御 + `logger.error` —— 历史上崩过 |
| 排除规则必须重新连续编号 | `resolve_input_paras` 里显式 `idx = len(self.rule_dict)`，注释写明「否则 rule_dict 下标出现空洞」 |
| 表达力天花板 | 只能表达 AND，不能表达 OR / NOT / 多结论独立权重 |
| 稠密矩阵 | 规则数 × Σ(每参数档位数)，99% 元素是 0 |

**结论**：矩阵是 1990 年代 fuzzykit 的实现遗产，numpy 时代它的唯一价值（向量化）可以用 dict + 循环以更直白的方式拿到。推理规模是百条规则级别，性能不是约束；可读性与可调试性的收益远大于性能损失。

## 3. 对照实验：改成什么样

真实 DB 数据（defect=ABERRATION / level=low，命中 12 条规则，7 个参数），对照 4 组：

| 参数 | 规则写的调整量 | S0 现状 | S2 只修聚合 | S3 全修 |
|---|---|---|---|---|
| BT | −2.00 ~ +2.00 | −0.0000 | −2.0000 | −2.0000 |
| CT | −2.00 | −0.0021 | −2.0000 | **−2.0000** |
| IP0 | +2.00 | +0.0063 | +2.0000 | **+2.0000** |
| IV0 | −2.00 ~ +2.00 | +0.0000 | +0.0000 | **+1.9987** |
| MBP0 | −1.00 ~ +1.00 | +0.5074 | +1.0000 | **+1.0000** |
| MSR0 | −2.00 | −0.4949 | −2.0000 | **−2.0000** |

- **S0** = 现状（生产代码原样跑）
- **S2** = 只修聚合（跨参数全局归一化 → 按参数分组归一化 + priority 加权平均）
- **S3** = 再修档位映射（按参数自己的 fuzzy_level 定位桶）+ 跨库去重 + 缺陷前件不当门控

倍数对比（`|产出 / 规则写的调整量|`，1.0 = 量级正确）：

| 参数 | S0 倍数 | S3 倍数 |
|---|---|---|
| CT | 0.001 | **1.000** |
| IP0 | 0.003 | **1.000** |
| MSR0 | 0.247 | **1.000** |

**结论**：档位映射与聚合两处必须同时修 —— 只修聚合，IV0 仍是 0（档位错位导致规则根本命中不了）；只修档位，量级仍然被摊薄。

> `CUSION` 是规则库专用参数，`ProcessParameter` 里没有对应列 → 取不到当前值 → 正反两条规则完全抵消 → 0.0000。这是**建议值不做可行性校验**的另一面（`recommended_value` 算完直接返回，0 处 clamp），与本次两处修正无关。

## 4. 改造方案（建议顺序）

| 阶段 | 内容 | 性质 | 依赖 |
|---|---|---|---|
| **E1 词法** | `split_phase` 改**最长后缀匹配**：档位词按长度降序，取最长可匹配后缀，`IV0_very_low` → (IV0, very_low)，不污染参数名 | 局部修 | 无 |
| **E2 档位映射** | 弃用全局 `HS_MAPPING_DICT` 查表；档位→桶索引改为**按参数自己的 `fuzzy_level` 取词表定位**（§1.2.2 方案 C）；三方词表收敛到后端一处权威定义（补齐 7/9 档，9 档需前端同步补） | 局部修 | E1 |
| **E3 聚合** | 跨参数全局归一化 → **按参数分组**归一化；priority 进组内加权（权重和为 1）；`delta = 组内激活度加权平均` | 设计修 | 无 |
| **E4 缺陷语义** | 明确缺陷在推理中的角色并落地（见 §5 待决 Q1）；修「只有缺陷前件则失活」 | 设计修 | Q1 |
| **E5 论域** | 论域权威源定案（见 §5 待决 Q2） | 需业务输入 | Q2 |
| **E6 矩阵** | `connected_matrix` 换成 dict + 循环（规则剔除不再需要重新编号） | 可延后 | E3/E4 |
| **E7 去重** | 跨库副本去重（1643 条记录里 1062 条是副本，占 64.6%；`IF MATERIALFLOWER_low AND IV0_high THEN IV0_reduce_2` 存在 9 份） | 数据治理 | 无 |

E1~E3 是**止损**：在它们落地之前，引擎算出的每一个数都不可信。

**E2 不依赖任何待拍板项**，且**不会破坏任何现存规则**：

- 修法已由 §1.2.2 实验确定（per-parameter 词表），不存在多个候选方案；
- 安全性已由 §1.2.3 全库体检背书（3440 个前件在目标算法下零不兼容、解释结果不变）；
- 唯一需要注意的边界：**档位词与参数档位数不兼容时（例：3 档参数写 `very_low`）应显式报错，而不是静默跳过**。现状 `nets.py` L629-632 的 `continue` 会把这类规则变成无声失活（§1.1）。E1/E2 落地时应同时把它改成可见的告警。
