## 1. 背景与目标

用户提问：**关键词默认 5 档，但规则只写了 low/medium/high，匹配上其实不全 —— 算法是怎么处理的？**

并给出判据：

> 算法不应做假设。关键词定义几档，就按几档构建参数向量，**而不是还要看规则是怎么定义的**。
> 规则按照向量格式进行映射，**能够填入的自然就填入了，无法填入的参数那就正常无法填入**。
> 然后下一步是计算隶属度，更匹配的规则会被推理出，而不匹配的规则匹配度会更低。
> 关键词的模糊等级和模糊规则**没有那么强的相关性**，只是最后匹配准与不准的区别。
>
> 所以我担心的点在于：算法中是否有什么操作**做了适配处理**。如果特意处理了，说明关键词和规则做了关联处理，那算法肯定有问题；如果没有做关联处理，那么算法就是合理的。

## 3. 决策记录

### D1（核心口径）档位词是**绝对词义**，规则**不需要**声明自己的档数体系

规则写 `low` 就是「偏低」这一档；它落在向量的哪一格，由**向量自己切了几格**决定：

| 向量档数 | 词表（按格序） | `low` 落格 |
|---|---|---|
| 3 | `[low, medium, high]` | 索引 0 |
| 5 | `[very_low, low, medium, high, very_high]` | 索引 **1** |
| 7 | `[extremely_low, very_low, low, medium, high, very_high, extremely_high]` | 索引 2 |

⇒ 5 档体系里 `low` = 索引 1 **是正确实现，不是缺陷**。
⇒ 规则**不需要**、也**不应该**声明「我是 3 档还是 5 档体系」——算法无需知道这件事。

### D2 三个机制经复核**不是**「适配处理」

| # | 机制 | 判定 |
|---|---|---|
| ① | `resolve_bucket` 按**字段自身词表**定位（`LEVEL_WORDS_BY_LVL[lvl].index(word)`） | **正确** —— 词填向量对应格 |
| ② | 每张词表必含 low/medium/high | **正确** —— 绝对词义下 5 档向量里必须有 low 这一格，3 档体系的规则写 low 正好填进去 |
| ③ | 桶中心等分 + `σ = span/(2(lvl-1))` | **正常** —— 标准等分模糊化 |

⇒ **P0-1 / E2 的诊断与修复都是对的**（原全局静态表会把 5 档向量上的 low 错填到 very_low 格）。

### D3 「档位语义平移」**不是风险**，是正常语义

5 档体系比 3 档体系多一个 `very_low` 在 `low` 之下 ⇒ `low` 自然上移一格。
⇒ 落格随字段档数变化**不列为问题**。
⇒ 真正的口径风险是**两条论域来源用了不同的 lvl**（权威 5 档 vs 推测硬编码 3 档）——
该问题已由 `2026-10-27` 文档 §18.3 关闭（推测论域 `lvl` 3 → 5）。

### D4（产品级准则）**规则库是渐进生长出来的，算法必须容得下不完整**

> 用户原话：「即使我的规则只有 low 相关的规则，那也只是匹配度低，而不是算法不能用，
> 我只需要不断补充规则，那么我的算法就会越来越准。」
> 「哪怕我只有一条规则可以用，或者没有一条规则能用，算法也是能正常运行的。」

推论：
1. **禁止对规则做严格约束** —— 不报错、不拒绝入库、不中断推理
2. 规则条件不满足 ⇒ 结果是**匹配度低**，不是「规则不能用」
3. 条件**填不进** ⇒ 同样按「匹配度最低」处理（该条件匹配度 0 ⇒ 该条规则激活度 0）+ WARNING
4. **直接否掉**的思路：规则必须声明档位体系 / 词表必须含全部词 / 入库强校验 / 规则不全则降级

**关键后续需求**：后续要实现「**从数据中自动整理出规则**」⇒ 规则是**动态变更**的，
自动生成的规则携带的档位词可能超出字段当前档数 ⇒ 该分支必须静默降级，不能抛错。

### D5 档位词填不进 ⇒ **整条规则不参与推理**（激活度 0），不是「删掉这个条件」

已实施（`fuzzy_core/models/nets.py` → `NumTskRuleNet._construct_numtskruleNet`）：

```python
unresolvable = False
for name, value in rule.r_preconditions.items():
    ...
    bucket = _resolve_bucket_safe(self.pre_dict[name]['lvl'], level, 'NumTskRuleNet.pre')
    if bucket is None:
        unresolvable = True      # 合法档位词但该字段档数不够 ⇒ 条件无法判定
        continue
    ...
if unresolvable and row_idx < len(self.connected_matrix):
    self.connected_matrix[row_idx][:] = 0   # 门控列清零 ⇒ 激活度 0
```

**为什么这样最省**：`tsk_inference` 里 `gate_cols.size == 0 ⇒ continue ⇒ 激活度保持 0`
是现成机制 ⇒ **推理层一行未改**，`too_weak` 闸自动剔除。

**严格区分**（这三种不是一回事）：

| 情形 | 处理 | 理由 |
|---|---|---|
| `worse` 等人工判断词 | 该前件不作门控，**规则其余条件照常** | 本来就没有隶属度可言 |
| `pre_dict` 里没有该维度 | 该前件不作门控，**规则其余条件照常** | 建不了论域（缺陷反馈未给程度等） |
| **档位词填不进词表** | **整条规则激活度 0** | 条件**无法判定** ⇒ 匹配度最低 |

### D6 「零可用规则 ⇒ 算法正常运行」在结构上已成立

| 层 | 现状 |
|---|---|
| 出库层 | `ResourceRepository.get_rules` **对规则无档案校验**（只有关键字侧有 `keyword_profile_issues` 跳过留痕）；库为空 → `return []` + WARNING |
| 推理层 | `engine.py` 推理调用有 try/except 兜底 ⇒ 异常不外溢 |
| 结论层 | 激活度 0 的规则不产出结论 ⇒ results 为空 ⇒ 上层空循环 ⇒ 返回空推荐 |
