# 模糊推理（FuzzyEngine）能力评估与改良路线

> 文档目的：回答三个问题 —— **模糊推理能解决什么问题 / 是否适用当前场景 / 怎么更准确**，并给出可执行的修改与优化规划。
>
> 文档性质：**讨论稿**。所有结论均基于 2026-10-20 对生产库（1646 条规则 / 183 个参数词条 / 11 个规则库）的实测与代码走查，不含未验证的推测。
>
> 范围：仅 `backend/process/algorithms/fuzzy/`（含 `fuzzy_core/`）。`empirical/` / `expert/` / `llm()` / `mining/` 不在本文范围。

---

## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| 模糊推理能解决什么问题？ | 把"参数状态判定"从硬阈值变成连续量，并据此把多条规则的调整量聚合成一个可信的建议。**它不预测调整结果，只做"偏离→纠偏"的映射。** |
| 是否适用当前场景？ | **适用，但当前实现没有把它的职责履行到位。** 架构骨架（双层分流 + 零阶 TSK）是合理的，不需要重写；但存在 3 个 P0 级语义缺陷，导致"哪些规则该激活"与规则作者意图**系统性错位**，输出的数值量级**不可信**。 |
| 怎么更准确？ | 分四层推进：**输入侧**（论域与隶属度贴合真实工艺）→ **规则侧**（跨库去重 + 特异性权重生效）→ **推理侧**（分组归一化 + 加权平均）→ **闭环侧**（迭代反馈）。其中推理侧 1 项改动可同时消除 3 个 P0 缺陷。 |
| 当前版本够用吗？ | 作为"**规则驱动的建议生成器**"够用（能给方向、给量级）；作为"**精确的工艺优化器**"不够用，且模糊推理本身也做不到 —— 后者应由 `expert/` 的物理模型承担，两者分工见 §5。 |

**最小修复路径**：3 个 P0 全部集中在两处代码 + 一处数据（详见 §4、§6），预计改动量 < 300 行，不触碰规则库结构与外部接口。

## 1. 模糊推理在做什么（理论定位）

### 1.1 三个能力，与本项目的对应关系

模糊推理相对"查表"多出来的能力只有三个：

| 能力 | 含义 | 本项目是否用上 |
|---|---|---|
| **C1 连续化状态判定** | 不问"注射速度是否偏低"（是/否），而问"偏低程度是 0.85" | ✅ 用上了，但映射错位（见 P0-1） |
| **C2 连续化调整强度** | 越偏离目标，建议的调整量越大，且是平滑过渡而非跳变 | ⚠️ 部分用上，被聚合方式破坏（见 P0-3） |
| **C3 多源共识聚合** | 多条规则各给一个调整量，按可信度合成一个 | ❌ 机制在（prod 连接 + 归一化），但归一化维度错了 |

**反过来说，模糊推理做不到的**（这些必须由别的地方补）：

- **不预测调整后的结果** —— 没有前向模型，无法回答"速度提到 30 会怎样"
- **不处理参数耦合** —— 一条规则只动一个参数，而注塑参数强耦合（速度↔压力↔时间）
- **不保证可行性** —— 建议值可能越界、可能与其它参数冲突
- **不保证最优** —— 没有目标函数与约束求解

### 1.2 当前实现用到的推理范式

代码走查确认，实际跑的是 **零阶 TSK（Takagi-Sugeno）**，不是 Mamdani：

```
IF X1_状态 AND X2_状态 THEN Y_add_数值        ← 规则形式
   ↓ FuzzyFeature: 高斯隶属度，5 档（very_low/low/mid/high/very_high）
   ↓ 规则层: prod(各前件在其指定档位的隶属度) = 规则激活度
   ↓ 归一化: 激活度 / Σ全部规则激活度
   ↓ 结论层: Σ(归一化激活度 × 规则结论值)
```

Mamdani（`FuzzyRuleNet`）与弹窗（`ParticularRules`）仅作兜底路径，规则库当前无 Mamdani 形式结论。

## 2. 规则库的真实语义模型（数据事实）

> 这一节是理解"模糊推理在解决什么问题"的基础。以下全部为生产库实测。

### 2.1 规则形态

```
IF SHORTSHOT_low     AND MEL_low THEN MEL_add_2
IF SHORTSHOT_medium  AND MEL_low THEN MEL_add_3.0
IF SHORTSHOT_high    AND MEL_low THEN MEL_add_3.8
```

| 维度 | 实测 |
|---|---|
| 规则总数（未删） | 1646 |
| 规则库数 | 11（`base` 通用 585 条 + 9 个产品库 30~276 条 + `expert_rules` 空） |
| 缺陷覆盖 | 17 个缺陷码，全部有 low/medium/high 三档 |
| 前件个数分布 | 2 个：1425 条；3 个：125；4 个：84；5+：12 |
| 结论参数 == 最后一个前件参数 | 1630 / 1646（99%）—— 规则体系基本自洽 |
| 缺陷前件位置 | 100% 在第一位（`_match_defect_level` 依赖此隐式约定） |
| 参数前件等级词 | `low` 853 / `high` 947 / `worse` 154 —— **零 `medium`** |
| 结论动作 | `add` 719 / `reduce` 828 / `adjust` 99（检查弹窗类） |
| 结论为百分比的规则 | 少量（如 `MSR0_reduce_30%`） |

### 2.2 关键发现：结论值由「缺陷档位 × 参数量纲」共同决定

实测每类参数有一套固定的三元结论值，严格对应缺陷的低/中/高档：

| 参数类别 | 实例 | low | medium | high |
|---|---|---|---|---|
| 速度/温度/压力 | IV0 IP0 PP0 PV0 BT CT NT | **2** | **3.0** | **3.8** |
| 时间/位置 | IT PT0 VPTL | **0.5** | **0.75** | **0.95** |
| 背压 | MBP0 | **1** | **1.5** | **1.9** |

**这条规律非常重要**：它说明规则作者的心智模型是

> **缺陷越严重 → 调整量越大**（在参数自身的量纲下）

也就是说，**缺陷档位不该是硬匹配，它承载着"调整强度"的语义**。而当前实现恰恰把它硬过滤掉了（只用来选规则集，选完就不再参与推理），导致：

> 同样是 `IV0_add_3.8`，严重缺陷和轻微缺陷给出的调整量**完全一样**。

这与规则库的编写意图**直接冲突**，是 §4 中"档位语义丢失"这一条的根因。

### 2.3 关键发现：同一业务规则在多个库中重复存放

以 `SHORTSHOT_high` 档位（31 条规则）为例：

```
参数 IV0  命中 7 条规则，结论值分布 {'3.8': 6, '10': 1}
   IF SHORTSHOT_high AND IV0_low  THEN IV0_add_3.8        <- base
   IF SHORTSHOT_high AND IV0_low  THEN IV0_add_3.8        <- R20230825161658
   IF SHORTSHOT_high AND IV0_high THEN IV0_reduce_3.8     <- base
   IF SHORTSHOT_high AND MEL_high AND IV0_low THEN IV0_add_3.8  <- R20230825161658
   ... 共 7 条
```

**同样的规则串在 `base` 和各产品库里各存了一份。** `RuleQueryService.get_rules` 的去重键是 `rm.id`（数据库主键），跨库记录 id 不同 → **去重完全失效**。

全库统计：同一 `(缺陷, 缺陷档, 结论参数, 结论值, 动作)` 的重复组有 **408 组**，最多的一组重复 9 次。

后果：这些副本在聚合时会**各自贡献一份 delta**，调整量成倍膨胀（详见 P0-3/P0-4）。

### 2.4 规则库的"两段式"结构

```
库层（离散路由）          规则层（连续推理）
────────────────────      ─────────────────────
product_category          IF 参数_状态 THEN 参数_调整量
polymer_abbreviation
defect_code
defect_level  ← 硬匹配    参数在论域中的位置 → 隶属度 → 激活度
```

**分层的合理性是对的**（离散条件不该塞进推理层），但 **defect_level 被划到了路由层**，于是 §2.2 说的"调整强度"语义在推理层丢失了。

## 3. 模糊推理在当前场景解决什么问题

### 3.1 适用性评估：适合，但只该承担"纠偏"职责

注塑工艺优化的完整能力可以拆成四层：

| 层 | 做什么 | 该由谁承担 | 现状 |
|---|---|---|---|
| L1 初始化 | 从零推导出合理的初始参数 | ✅ `expert/` 物理模型（`v_inj = f(MFI, L/t, 模温)`） | 已有，独立体系 |
| L2 纠偏 | 已知缺陷 → 偏离了哪些参数 → 调多少 | ✅ **模糊推理的战场** | 骨架对，语义错 |
| L3 约束求解 | 保证调整后参数互相自洽、仍在可行域 | ❌ 缺 | 应由优化器承担 |
| L4 结果预测 | 调完之后会怎样 | ❌ 缺 | 需仿真或前向模型 |

**结论：模糊推理放在 L2 是对的** —— 它的输入（缺陷 + 当前参数）刚好是"可观测的离散事件 + 连续的参数状态"，输出（要调哪些、调多少）也刚好是"离散建议 + 连续量值"。这正是模糊推理的甜区。

但要注意：**不要指望它做 L3/L4**。当前 `_merge_layer_results` 已经在做一点 L3 的雏形（同参数聚合），却因为聚合方式错误，反而制造了噪声。

### 3.2 它当前实际在做的事（逐条核对）

| 场景需要 | 模糊推理能否提供 | 当前实现是否提供 |
|---|---|---|
| 判断"注射速度偏低" | ✅ 隶属度 | ❌ 档位错位，算成"极低" |
| 给出"提高多少" | ✅ 规则结论值 | ⚠️ 量级被稀释/放大 |
| 避免临界抖动 | ✅ 连续隶属度 | ✅ 这块是对的 |
| 多规则共识 | ✅ 加权聚合 | ❌ 归一化维度错 + 跨库副本重复计入 |
| 冲突提示 | ⚠️ 需显式建模 | ❌ 同参反向时简单相消 |
| 解释"为什么这么调" | ✅ 规则可追溯 | ⚠️ 落库无 rule_refs 溯源 |
| 预测调后结果 | ❌ | ❌ |
| 保证参数自洽 | ❌ | ❌ |

### 3.3 模糊推理 vs 物理模型：不是替代关系

项目里已有 `expert/algorithm_engine`（2426 行，基于材料流动率、流长比、模温的物理推导）。两者**不是同一层的东西**：

```
物理模型（expert）：  材料 + 模具 + 机台  →  参数应该是多少      （正向，可验证）
模糊规则（fuzzy）：   当前参数 + 缺陷现象  →  偏离了怎么拉回来    （反向，经验）
```

工程上正确的组合是：**物理模型给初值 → 模糊规则做迭代纠偏 → 物理模型复检新值是否仍合理**。目前这条闭环没有建立（`iteration_trend` 未接入），是后续的明确改进点。

## 4. 当前实现与设计意图的偏差清单

> 每条都有实测证据。设计意图出处：`_refs/system/ai/fuzzy-engine-reference.md` §7。

### P0-1 等级映射整体错位一档

**事实**
- 全部 183 个 parameter 词条的 `fuzzy_level = 5` → 论域分 5 档
- `FUZZY_LEVELS[5] = ['very_low', 'low', 'mid', 'high', 'very_high']` → 桶位 0..4
- `HS_MAPPING_DICT` 用的是 **3 档语义**：`low→0, mid/medium→1, high→2`

**后果**：规则写 `IV0_low` 命中的是 **very_low** 桶；写 `IV0_high` 命中的是 **mid** 桶（不是 high！）。规则库里参数前件只有 `low`/`high`（零 medium），等于**所有规则被系统性拉低一档**。

**实测**（SHORTSHOT_high，同一批规则，改映射前后）

| 规则 | 当前激活度 | 修正后 (low→1, high→3) |
|---|---|---|
| `PP0_low` | 0.1070 | **0.9935** |
| `IV0_low` | 0.2494 | **0.9460** |
| `IT_low` | 0.2780 | **0.9231** |
| `IP0_low` | 0.0198 | 0.7261 |
| `MBP0_low` | **0.6065** | 0.0111 |

激活度排名直接翻转。

**旁证**：`HS_MAPPING_DICT` 中 `level1..level9 → 0..8` 这套**是 5 档正确的**，说明映射表按 3 档编写，而数据库用 5 档 —— 两套约定从未对齐。

**附带隐患**：`ALL_LEVEL_WORDS` 收录了 `very_low / very_high / extremely_low / extremely_high`，但 `HS_MAPPING_DICT` 没有这四个键。`is_level_word()` 放行 → `HS_MAPPING_DICT[level]` **KeyError**。当前不崩仅因规则库未使用这四种词。

---

### P0-2 参数论域与真实工艺值不匹配

**事实**：论域直接取 `RuleKeyword.range_min/range_max`，数据未按真实工艺校准。

| 参数 | 实测值 | 论域 | 状态 |
|---|---|---|---|
| BT 料筒温度 | 220 | 0–50 | 超上限 4.4× |
| MEL 计量终止位置 | 758.07 | 0–200 | 超上限 3.8× |
| PT0 保压时间 | 15 | 0–10 | 超上限 |
| MBP0 储料背压 | 5 | 10–50 | 低于下限 |
| IV0 / IP0 / PP0 / PV0 / IT | 25 / 70 / 37 / 14 / 4 | 各自区间 | 正常 |

**后果**：高斯隶属度在论域外 ≈ 0 → **涉及这些参数的规则永远不激活**。这就是 `BT` / `MEL` / `PT0` 相关规则激活度恒为 `0.0000` 的原因（不是算法算错，是根本没进门）。

---

### P0-3 聚合方式错误：全局归一化 + 直接累加

**事实**（`fuzzy_core/models/nets.py` `tsk_inference` + `fuzzy_algorithm._merge_layer_results`）：

```
激活度归一化：new_activations = rule_activations / Σ(全部规则激活度)   ← 全局
优先级加权：  activations_with_priority = new_activations * priority_array
结论聚合：    merged[p].delta += rec.delta                              ← 累加
```

**与设计意图的偏差**：参考文档 §7.5 举例写的是"归一化后激活度 ≈ 0.567 (10/(10+5))" —— 分母是**同组**激活度之和。当前实现是全局归一化，等于先把所有参数的激活度摊薄，再各自累加。

**三重伤害**（互为因果）：

1. **稀释**：10 个参数分摊激活度，每个参数的调整量被压到接近 0
2. **副本膨胀**：§2.3 的跨库副本各贡献一份 delta
3. **反向抵消**：同参数的正负规则简单相加，互相抹平

**实测**

| 参数 | 当前（累加） | TSK 加权平均 | 差 |
|---|---|---|---|
| inj_pres_1 | +0.04 | **+3.80** | 94× |
| inj_spd_1 | +0.375 | **+2.21** | 6× |
| met_back_pres_1 | +0.62 | +1.90 | 3× |

以 `IV0` 为例，`SHORTSHOT_high` 档有 6 条 `+3.8` 副本 + 1 条 `-3.8`。**正确结果应该在 [-3.8, +3.8] 区间内**，而累加会冲出这个区间。

**好消息**：改成"**按输出变量分组归一化 + 组内加权平均**"，一次性解决上面三条 —— 因为分母会包含所有副本，副本多的参数不会被放大；反向规则按激活度加权而非简单相消。

---

### P0-4 跨库规则副本未去重

**事实**：`get_rules` 去重键为 `rm.id`，跨库记录 id 不同 → 失效。同一业务规则在 `base` 与产品库各存一份，全库 **408 组重复**。

**与设计意图的偏差**：参考文档 §6.2「三级特异性匹配」+ §7.3「priority 协议（L1=10 / L2=5 / L3=4 / L4=1）」的本意是"产品专用规则权重高于通用规则"，从而让同一规则在多库的副本**不冲突**（专用库占主导，通用库副本权重低）。

**但 priority 协议从未落实**：全库 1646 条 `RuleMethod.priority` **全部 = 1** → `priority_array` 全 1 → `activations_with_priority = new_activations × 1`，加权形同虚设。

⇒ 现状是：**产品专用规则（碗 276 条）与通用规则（base 585 条）权重完全相同**，一起被累加稀释。

---

### P1-1 缺陷档位的"调整强度"语义丢失

见 §2.2。当前 `_match_defect_level` 把缺陷档位当硬过滤器用掉，档位信息没有以任何形式进入推理权重。

**规则库本意**：缺陷 low→2 / medium→3.0 / high→3.8，档位直接编码在**结论值**里；而**前件的缺陷档位**又做了一次档位过滤。同一信息在规则里表达了两遍，引擎只用了第一遍。

**待定**：是让引擎按缺陷档位额外加权（乘数），还是认为结论值已编码档位、引擎不重复处理。**这是一个业务语义决策，不是技术问题。**

---

### P1-2 缺陷档位过滤依赖隐式约定

`_match_defect_level` 只看 `preconditions[0]`，且当首前件不是缺陷名时直接 `return True`（放行）。当前 1646 条 100% 符合，但这是数据巧合不是契约 —— 规则库一旦新增非该格式规则，档位过滤会**静默失效**，不同档位的规则混在一起推理。

---

### P1-3 兜底论域语义可疑

`_load_keyword_dicts` 在 `RuleKeyword` 缺失时兜底：`lvl=3, min_val=0, max_val=current×2` —— 把当前值当成"中档"、用当前值×2 当上限。这套 3 档语义与主路径的 5 档不一致，且"当前值 = 中档"这个假设没有依据。

---

### P1-4 检查类建议在 suggestion 分组中被整批过滤

**事实**（2026-10-20 实测 `FLASH_low` 场景）：

规则 `IF FLASH_low AND CLAMP_worse THEN CLAMP_adjust_请检查锁模力是否不合理。` 正常产出了建议：

```
{'param': 'CLAMP', 'param_label': 'CLAMP', 'source': 'fuzzy.check',
 'direction': 'check', 'reason': '模糊推理建议：请检查锁模力是否不合理。'}
```

但它**没有出现在 `suggestion.groups` 里**。原因在 `parameter_optimize._build_suggestion_payload` 的“一致性过滤”：

```python
filtered_recs = [rec for rec in algorithm_recommendations
                 if _to_business_param_name(rec.get("param")) in baseline]
```

`CLAMP`（锁模力）**不在 `ProcessParameter` 里**（它是机台参数，不是工艺参数列），翻译后仍是 `CLAMP`，不在 baseline → 被过滤。

**后果**：规则库里 **99 条检查/弹窗类规则的结论，工艺员在 UI 上永远看不到**。它们仍会落进 `Recommendation.recommendations` JSON，但前端只渲染 `suggestion.groups`。

**附带问题**：这类建议的 `param_label` 直接回退成 `CLAMP`（无中文名），`current_value` 回退成 `0.0`（baseline 里查不到）。

## 5. 准确性提升路线

### 5.1 分层框架

```
输入侧 ──→ 规则侧 ──→ 推理侧 ──→ 输出侧 ──→ 闭环侧
 感知准     知识准     聚合准     可用      可自我修正
```

### 5.2 输入侧：让"参数状态"感知准确

| 改进项 | 做法 | 预期收益 |
|---|---|---|
| **论域校准** | 用历史 `ProcessParameter` 数据的分位数（如 5%~95%）重算 `range_min/range_max`；或至少人工修正 BT/NT/MEL/PT0/MBP0 | 直接激活原本"永不出场"的规则（当前占相当比例） |
| **论域动态化** | 用"当前值 ± 工艺容差"替代静态量程 —— 注塑的"高/低"本就相对该产品/该材料的正常区间 | 同一套规则能跨产品复用 |
| **隶属度函数选型** | 现为高斯，`sigma = (max-min)/(2×(lvl-1))` 固定。工艺参数的状态判定常带**单侧性**（注射速度"偏低"才需调，不偏高的部分不需要） | 三角/梯形隶属度更贴合 |
| **论域外兜底** | 值超出论域时 clip 到边界而非自然衰减到 0 | 越界参数仍能参与推理 |

### 5.3 规则侧：让"知识"准确

| 改进项 | 做法 |
|---|---|
| **跨库副本去重** | 按业务内容 `(defect_code, 规则串)` 去重，保留 specificity 最高的那条（或按 priority 取最高） |
| **priority 协议落实** | 按 §7.3 的 L1=10 / L2=5 / L3=4 / L4=1，由 `specificity` 自动推导写入 `RuleMethod.priority`（一次性数据迁移脚本） |
| **`worse` 前件显式化** | 154 条 `worse` 规则目前是"该参数不合理"的人工判断 —— 可转为与 `adjust` 同级的检查类输出，或建独立"参数合理性"词表 |
| **规则覆盖度体检** | 17 缺陷 × 3 档 × 参数的矩阵化体检报表，标出空洞与冲突 |

### 5.4 推理侧：让"聚合"准确 ★ 最高性价比

**核心改动（P0-3 + P0-4 一次解决）**：

```
① 归一化维度：全局 → 按输出变量分组
   w_i = activation_i / Σ_{j: output_j = output_i} activation_j

② 组内聚合：累加 → 加权平均
   delta_p = Σ_{i: output_i = p} w_i × z_i
```

**附带效果**：
- 每个参数的激活度之和回归 1 → 调整量回到规则作者写的量级（2 / 3.0 / 3.8）
- 跨库副本不再放大（分母包含副本）
- 同参反向按激活度加权，而非简单相消
- 输出值天然落在 [-max, +max] 区间内

**配套改动**：
- 启用 `MIN_ACTIVATION_THRESHOLD`（0.01001）过滤近零激活度规则 —— 这会消除当前那批"置信度接近 0 却产出建议"的噪音
- `confidence` 语义重定义（当前 `activation_sum / rule_count` 含义不清，建议改为组内激活度集中度或主导规则占比）

### 5.5 输出侧：让结果"可用"

| 改进项 | 说明 |
|---|---|
| **规则溯源** | `Recommendation` 带上命中的规则串 / `rule_refs`，让工艺员知道"为什么调这个" |
| **冲突显式化** | 同参数同时存在 add 与 reduce 且权重接近时，标记为"存在争议"，而不是静默相消 |
| **量纲与边界校验** | 建议值超出 `range_min/range_max` 时截断并标注 |

### 5.6 闭环侧：让系统能自我修正

| 改进项 | 说明 |
|---|---|
| **`iteration_trend` 接入** | 调整后缺陷改善 → 强化命中规则；恶化 → 抑制。当前 `_trend_to_factor` 已有 5 个系数，但 `iteration_trend` 从未传入 optimize 链路 |
| **调后复检** | 用 `expert/` 物理模型校验新参数是否仍在合理区间（"模糊给建议，物理做把关"） |
| **规则效果回溯** | 累积"哪条规则 → 哪个缺陷 → 调后是否改善"，反哺 priority 分级 |

### 5.7 推进节奏建议

| 阶段 | 内容 | 依赖 | 风险 |
|---|---|---|---|
| **阶段 1** | P0-1 档位映射 + P0-2 论域校准 | 无（映射表 + 数据） | 低。纯"让它按设计意图工作" |
| **阶段 2** | P0-3/P0-4 分组归一化 + 加权平均 + 跨库去重 | 阶段 1 | 中。**改变输出量级**，需与工艺员对量级 |
| **阶段 3** | P1-1 缺陷档位权重（业务决策）+ 激活度阈值 + confidence 语义 | 阶段 2 | 中 |
| **阶段 4** | 5.2 动态论域 / 隶属度选型 | 阶段 3 | 中高。需要历史数据支撑 |
| **阶段 5** | 5.6 闭环反馈 | 阶段 4 | 高。依赖 `iteration_trend` 链路 |

**阶段 1 是"止损"**：在档位映射与论域修正之前，所有调参都是在拟合一个错误的激活函数。
