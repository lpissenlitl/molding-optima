## 一、本次 Session 完成的全部工作

### 1.1 修复登录态校验 Bug（request.ts）

**问题**：`UNAUTHORIZED_STATUS` 列表混入了业务错误码，导致：
- 业务错误（如数据不存在 1004）被误判为认证错误 → 莫名其妙跳登录页
- 同时路由切换到无 API 的页面时（Dashboard、占位模块），永远不校验（因为没 API 调用触发 401）

**根因**：历史上列表是 `[101001, 1004, 1005, 1007, 1009]`，其中只有 `101001`（ERROR_USER_TOKEN_NOT_EXISTS）是真正的认证错误，其余都是业务错误。

**修复**：
- 精简列表为 `[101001]`
- `window.location.replace('/login')` → `router.push({ path: '/login', query: { redirect } })`，避免整页刷新

### 1.2 路由守卫主动校验 token 过期（permission.ts）

**问题**：上述修复只覆盖"主动 API 调用触发 401"的场景。**纯静态页面**（Dashboard、Placeholder 业务模块）即使 token 过期也不会触发任何校验，用户能继续访问。

**方案**：在路由守卫里基于 `token_expires_at` 做**本地过期检查**——成本极低（一次字符串比较），每次路由切换都执行。

**实现链路**：

```
后端 login() 返回 user_dict + {token, token_expires_at}
            ↓
前端 userStore.applyUser() 写入 token_expires_at
            ↓
permission.ts 路由守卫：每次 to 之前检查 token_expires_at < now
            ↓
过期 → userStore.clear() + router.push('/login?redirect=...')
```

#### 后端改动（2 处）

1. **`identity/services/user_service.py:create_token()`**
   - 返回值由 `raw_token` → `(raw_token, expires_at)`
2. **`identity/services/user_service.py:login()`**
   - `user_dict.update({"token": token})` → `user_dict.update({"token": raw_token, "token_expires_at": token_expires_at})`

#### 前端改动（3 处）

3. **`stores/user.ts`**
   - `UserInfo` 加 `token_expires_at: string`
   - `EMPTY_USER_INFO` 加 `token_expires_at: ''`
4. **`permission.ts`**
   - 加 `isTokenExpired()` 工具函数
   - 已登录分支前置 token 过期检查
5. **`utils/request.ts`**（已在 1.1 修复，保留 101001 兜底）

## 二、技术决策

### 2.1 为什么本地校验而非每次调 `/api/profile/`？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **本地 expires_at 校验**（选用） | 零网络成本、即时响应 | 客户端时间不准会导致误判 |
| 每次调 `/api/profile/` | 后端权威校验 | 每次路由切换多一次 API 请求 |
| 定时轮询（如 5min 一次） | 平衡 | 实现复杂、有窗口期 |

**选用本地校验的核心理由**：
- Token 默认 6h 过期，但 `flush_token()` 在剩余 < 3h 时自动续期（`models/user.py:337-340`）——活跃用户 token 几乎不会过期
- 客户端时钟偏差影响很小（误差几秒不影响"6 小时过期"判断）
- 后端 101001 仍兜底，**双保险**——即使本地判断错了，API 调用也能纠正

### 2.2 token_expires_at vs user.expires_at

`user.expires_at` 是**用户账号有效期**（公司失效即失效），`Token.expires_at` 是**会话有效期**（默认 6h）。

前端原本的 `UserInfo.expires_at` 实际是 user.expires_at（来自 `construct_user_info() → to_dict()`），**不是 token 有效期**。所以必须新增独立的 `token_expires_at` 字段，不能复用。

### 2.3 为什么不在 request.ts 加全局定时刷新？

定时刷新（如每 30 分钟调一次 `/api/profile/`）：
- 实现复杂（要在合适生命周期启动/停止）
- 后台页面静止时浪费资源
- 路由守卫**已经覆盖**了"每次切换"这个最关键场景

**结论**：路由守卫足够，不需要定时刷新。

## 七、反思与教训

### 7.1 不要把业务错误码混入认证错误列表

`UNAUTHORIZED_STATUS` 这种白名单**必须严格只放认证错误**。业务错误即使名字像"用户相关"也不应该混进来。

> 已记入 memory

### 7.2 兜底 ≠ 唯一防线

request 拦截器里的 101001 处理只是**被动**兜底——必须有 API 调用触发。对于无 API 的纯前端页面，必须有**主动**防线（路由守卫、组件 mount 时检查等）。

### 7.3 后端返回时间字段用 ISO 8601 字符串

`token_expires_at` 是 `DateTimeField` 转 ISO 字符串，前端直接 `new Date(...).getTime()` 比较。前后端时间字段统一约定：
- 数据库：DateTimeField（带时区）
- API：ISO 8601 字符串
- 前端：转 epoch ms 后比较
