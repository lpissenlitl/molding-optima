## 1. 为什么要做：一个闭合的因果链

### 1.1 从「短射为什么不先调充填量」说起

用户的业务口径是：**短射 / 飞边的第一优先是充填量（`IL` 注射行程、`MEL` 计量终点位置），充填量到位后才轮到注射压力 `IP`、注射速度 `IV`，再往后是温度 / 保压类。**

规则库**完全按这个口径写的**（短射 109 条规则的结论参数排序，实测）：

```
MEL(23)  IV0(21)  IT(17)  MBP0(10)  PV0(7)  BT(7)  PP0(7)  PT0(4)  IP0(4)  NT(4)  IV1(3)  IP1(1)  BT1(1)
```

`MEL` 以 23 次高居首位 —— **规则库没问题**。问题在算法判不出档，而断点非常具体。

短射规则长这样：

```
IF SHORTSHOT_low    AND MEL_low THEN MEL_add_2      # 充填不足 ⇒ 把充填量加上去
IF SHORTSHOT_medium AND MEL_low THEN MEL_add_3.0
IF SHORTSHOT_high   AND MEL_low THEN MEL_add_3.8
```

注意前件写的是 **`MEL_low`**（计量终止位置偏低 ⇒ 充填不足）。

而 `MEL` 的判级论域是 **`[0, 200]`**（`RuleKeyword.range_min/max` 的经验域）。取真实工况 `condition=1`：

```
MEL 当前值 = 184.54 mm
论域 [0, 200]，5 档 ⇒ 桶中心 0 / 50 / 100 / 150 / 200，σ = span / (2×(lvl−1)) = 200/8 = 25
```

| 规则要求的桶 | 桶中心 | 隶属度 μ | 门控阈值 τ=0.1353 | 判档结果 |
|---|---|---|---|---|
| `MEL_low`（25% 分位） | 50 | exp(−((184.54−50)/25)²/2) = **2.7e−5** | 2.7e−5 ≪ 0.1353 | 判不出"低"档 |
| `MEL_high`（75% 分位） | 150 | exp(−((184.54−150)/25)²/2) = **0.385** | 0.385 > 0.1353 | 判成"高"档 |

⇒ **短射场景下 `MEL` 的真实值被判成「高」档，而规则要的是「低」档 —— 档位判反了。**

这不是偶发：诊断报告实测 81 条真实工况，`MEL` 真实值区间 **121.99 ~ 758.07**，而论域固定 `[0, 200]`：

- 121.99 ~ 200（61%~100% 分位）⇒ 落在**高/极高**档 ⇒ `MEL_low` 判不出、`MEL_high` 判得出
- \> 200（越界 61%~379%）⇒ 全部桶 μ ≈ 0 ⇒ 任何档都判不出

⇒ **两种情况都对短射规则不利**：要么档位判反，要么判不出。
⇒ 23 条 `MEL` 短射规则判不出档 ⇒ **充填量这个"第一顺位参数"根本进不了推荐列表** ⇒ 引擎只剩恰好判得出档的 `IV0`/`IT`/`MBP0`/`PP0` 可推。

**这就是「注射量没怎么调整」的算法层原因**：不是规则没写，不是优先级没排，是 `MEL` 的判级基准整个错了 ⇒ **该调的参数没被调、调的参数排序被挤到后面**。

> 📌 **定性口径**（沿用此前约定）：这是「**判档不准 / 判档区分度低**」，不是「算法不能用」。
> 引擎照样出推荐值，问题在于**参数选得不对、方向可能反**。B1 的目标是让**参数取值本身**更准，而不是"把规则激活率刷高"。

### 1.2 论域在推理链路里扮演什么角色

```
RuleKeyword.range_min / range_max           ← 经验域（当前唯一的下界来源）
        ↓  library/adapters.py::_attr_to_profile
KeywordProfile(min_val, max_val, step, lvl)
        ↓  engine._apply_device_bound()       ← 只换上界（7 个必填族），下界不动
        ↓  macros.bucket_centers(lo, hi, lvl)  ← 论域等分成 lvl 个桶
        ↓  高斯隶属度 ⇒ 每个桶一个 μ
nets.py::M-1 门控                            ← μ < GATE_TAU(0.1353) ⇒ 该桶判不出
```

⇒ **论域 = 规则里 `X_low` / `X_high` 的判级坐标轴**。坐标轴画偏了，规则写得再对也判错档。

### 1.3 判档失准的四种表现（现状全貌）

用生产实际论域（**含设备上界替换后**）与 `condition=1` 真实值对照：

| 表现 | 说明 | 实例（真实论域 → 当前值 → 落点） |
|---|---|---|
| **① 越上界** | 当前值被排除在论域之外 ⇒ 任何档都判不出 | `NT` 喷嘴温度 `[0,50]` → 250 → **上界外 400%**（🟢 B1-1 已修为 `[200,280]`，250 落 62.5% 分位，见 §6.2 结论 4）<br>`MP0` 熔胶压力 `[0,10]`（设备上限）→ 18 → **上界外 80%**<br>`IL0` 注射位置 `[0,150]` → 174.63 → 上界外 16% |
| **② 越下界** | 同上，方向相反 | `VPTL` 切换位置 `[30,60]` → 16.65 → **下界外 45%** |
| **③ 挤在边角** | 全部样本落同一档（`X_low` 恒判中、`X_high` 恒判不出） | `CT` 冷却时间 `[0,120]` → 5 → **4% 分位**<br>`IT` 注射时间 `[0,20]` → 1.6 → 8% 分位<br>`PT0` 保压时间 `[0,10]` → 1.88 → 19% 分位 |
| **④ 退化域** | min ≥ max ⇒ σ=0 ⇒ 隶属度恒 0 | `IL` 注射位置 `[0,0]`、`VPTM` 切换方式 `[-1,-1]` |

> 📌 以上都是**判档不准**（区分度低），不是"算法不能用"。引擎在这些参数上仍会出建议，只是判出来的档不可靠。

### 1.4 为什么"去改规则库"救不了

规则里的 `X_low` / `X_high` 是**绝对词义**（"这个参数偏低/偏高这一档"），它落在坐标轴哪一格，由**该字段自己的档位数**决定 —— 这是 `macros.LEVEL_WORDS_BY_LVL` 已定好的口径（B3 落地时确认过）。

⇒ 要改的是**坐标轴（论域）的位置**，不是规则里的话。
⇒ 把规则从 `MEL_low` 改成 `MEL_high` 能让它判对一次，但下次换台设备、换个件，坐标轴又偏了 —— **治标不治本**。

## 2. 关键认知修正：判级基准 ≠ 设备物理上限

这是整个 B1 最核心的一句话，也是当前实现最根本的问题。

### 2.1 两种「上界」被混成了一种

| 概念 | 含义 | 用途 | 现状 |
|---|---|---|---|
| **物理天花板** | 机器能设的最大值 | **裁剪推荐值**（建议不能超过它） | ✅ `resolve_param_limits` 已实现 |
| **判级基准** | 划分 low/medium/high 的坐标区间 | **判规则命中哪一档** | ❌ `resolve_domain_limits` 错用了物理天花板 |

当前 `specs.py` 里两者的注释写得很清楚：

```python
# 判级论域上界（必填等级字段：用设备实测值替换论域上界）
"IP":  "max_set_injection_pressure",      # 注射压力
...
```

⇒ 一台 140 MPa 的机台，"注射压力高" 的判级上界就是 140 MPa。工艺员设 20 MPa 时落在 14% 分位 ⇒ 规则写 `IP0_high` 判不出、写 `IP0_low` 恒判中。**"能不能压得更高" ≠ "算不算高"，被混成一件事了。**

### 2.2 这个混淆已经造成两处实测问题

**问题一：设备上限比当前设定还小 ⇒ 论域把「当前状态」判成越界**

`condition=1` 的机器 `max_set_metering_pressure = 10` MPa，而该工况 `MP0 = 18` MPa：

```
MP0 论域 [0, 10]（设备上限替换后），当前值 18 ⇒ 上界外 80%
```

⇒ 引擎认为「熔胶压力已经严重超限」，而当前设定就是 18。`_apply_device_bound` 只有 `new_max <= profile.min_val` 的守卫（防退化域），**没有「设备上限不得小于当前设定值」的守卫**。
⇒ 这类数据一旦录入，该参数的建议方向会整体反向。

**问题二：单位口径不一致**

`CLAMP` 锁模力：`RuleKeyword.unit = kN`、论域 `[0, 50]`；设备侧 `max_clamping_force = 160` **ton**（≈1568 kN）。
⇒ 引擎取到哪个都会判不准。
⚠️ **算法层不做单位换算**（既有口径：取的就是界面值）⇒ 这一项必须**先由数据侧统一单位口径**，引擎再取用，否则改了也是错的。

### 2.3 B1 的口径修正（写进代码前先定死）

> **判级基准 = 「这个场景下的合理工艺区间」**；
> **物理天花板 = 「这台机器能设的上限」**；
> 两者**不混用**：物理天花板只用于裁剪推荐值，判级基准另有来源。
>
> **论域来源只认权威维度**：设备维度 / 材料维度 / 产品维度。
> 三者都没到位时 ⇒ **回落经验域**（`RuleKeyword.range_min/max`），照常出推荐值，**不报错、不阻塞**。
> **不得拿实测值当论域来源。**

据此，论域基准按**参数族**分层，各族有自己的权威源（见 §3）。

**口径更正（2026-11-10，设定值类分层）**

⚠️ 上面的原始表述与 **B1-3（按 Q1 拍板）已落地的做法相反**：B1-3 正是「拿设备上限替换设定值类的判级论域上界」。
⇒ 两套口径在真实数据上正面冲突（§6.5 有首次实证），**本节把它更正成分层口径**：

| 概念 | 职责 | 落地位置 | 状态 |
|---|---|---|---|
| **物理天花板**（设备 `max_set_*`） | ① **裁剪推荐值**（建议不得超它） | `engine._apply_machine_limits` | ✅ 已实现 |
| | ② **越限阻断**（超了就 400） | `parameter_optimize._guard_blocking_over_limits` | ✅ 已实现 |
| | ③ **设定值类的判级论域上界** | `specs.resolve_domain_limits` | ✅ **保留**（本节更正的对象） |
| **判级基准** | 划分 low/medium/high 的坐标区间 | 温度类=材料区间 / 位置类=设备行程 / 产品类=制品级物理基准 / **设定值类=设备上限（唯一例外）** | ✅ 已实现 |

**为什么设定值类保留设备上限**（两条理由 + 一条实测反证）：

1. **业务语义成立**：「合理设定上限确实随机台能力变」—— 同一台机跑不动 200 MPa 的注射压力，那「注射压力高」对这台机就没有意义；设定值类的档位词本来就是**相对本机能力**说的。
2. **H1 守卫兜住病态场景**：设备上限 < 当前设定值（实测 `MP0` 设定 18MPa / 机台上限 10MPa）⇒ 不替换、保留经验域并留痕（见 §5 B1-3 落地记录）⇒ **不会把「当前状态」判成越界**。
3. **实测反证（撤销会更差）**：真实库 **56 工况 / 设定值类 15 参数 / 804 样本**，同档占比（越低越好；「判不出档」单列一桶计入分母）：

   | 判级论域口径 | 平均同档占比 | 样本池同档占比 |
   |---|---|---|
   | ① **设备上限域（现状）** | **91.52%** | 91.54% |
   | ② 纯经验域（= 撤销 B1-3） | **96.66%** | 96.64% |
   | ③ 设备上限 × 0.9 | 91.02% | 91.04% |
   | ④ max(设备上限, 当前设定值) | 91.39% | 91.42% |
   | ⑤ min(设备上限, 经验域上界) | 91.27% | 91.29% |

   ⇒ 撤销设备上限（②）会**恶化 5.14pp**；而所有「带设备上限」的候选都落在 91.0~91.5% 的窄带里 ⇒ **设备上限这一层是主要贡献**，收紧/改写它的收益 ≤ 0.5pp，不值得动口径。
   （逐参数明细见 §6.6.5；`IV0` 是「设备域更差」、`PV1` 是「设备域更好」的两个典型，`MP0` 是 H1 守卫的典型受益者。）

⇒ **一句话口径更正为**：**「除设定值类外，判级基准 ≠ 设备物理上限」**。
   设定值类是**唯一**把设备上限当判级上界的族，且有 H1 守卫 + 越限阻断双层保护。

## 3. 论域来源：按参数族分层

### 3.1 分层原则（三条）

1. **上界优先取「材料/产品窗口」**（材料能夹紧的，必须夹紧）—— 温度类已现成；
2. **其次取「设备维度」**，但**必须留守卫**：设备上限 ≤ 当前设定值 ⇒ **不替换**（保留经验域）并在诊断里留痕 —— 不用当前值去顶边界（那等于拿实测值定论域）；
3. **没有权威维度 ⇒ 回落经验域**，照常出推荐值，**不报错、不阻塞**；该参数在诊断清单里标记来源，便于后续补权威源。

### 3.2 六族总表

|---|---|---|---|---|---|---|

### 4.2 G6：位置类论域上界的两难（实测新发现，B1-2 必须处理）

探针实测：**位置类真实值有 131/53 条超出该机螺杆行程**（例：`cond=93` 行程 200mm 而 `MEL`=758.07mm、`IL0`=716.62mm）。追查这批值的物理来源：

```
MEL          = met_pos_1 + pst_met_decomp_dist          ✓ 实测 8/8 精确吻合
met_pos_1    = cushion_len + total_len                   ✓ 专家引擎算法 #14
total_len    = (制品重 + 流道重) / 熔体密度 × 1000 / 螺杆截面积
```

⇒ **位置类真实值是「产品维度」物理推导量，不是随手填的数**。而 `total_len` 只跟制品重量、熔体密度、螺杆直径有关，**没有跟机台行程做校验** ⇒ 当「制品很重 + 螺杆很细」时，推出来的位置就超过机台行程。

**这带来一个必须回答的问题：论域上界用行程，会不会把「脏数据」洗成「合法值」？**

| 方案 | 做法 | 问题 |
|---|---|---|
| **甲（直取行程）** | 论域 = `[0, 行程]` | 758mm 落在 220mm 论域外 ⇒ **判不出档**（回到今天的病）；但**暴露**了脏数据 |
| **乙（行程×系数）** | 论域 = `[0, 行程 × k]` | 把脏数据“合法化” ⇒ **掩盖**了选机/录数据的错；但不会越界 |
| **丙（双上界）** | 论域上界 = `max(行程, 实际值)` | **拿实测值当论域来源** ⇒ 已被既定口径否决 |

**B1 取甲，但加一道守卫（不报错、不阻塞）**：

1. 论域上界 = `max_injection_stroke`（权威维度，用户已定）；
2. **当前值 > 行程** ⇒ 该参数**不判档**（视同缺权威源），走**回落经验域** + 诊断留痕 `domain_source='kept_experience_domain', reason='value_exceeds_device_stroke'`；
3. **不阻断推理**（不 400）—— 因为「制品超机台能力」是**选机/录数据**层面的事，不是算法该拦的；
4. 诊断清单单独列出「位置类值超行程」的工况，**交数据侧核查**（这才是真正该报出去的东西）。

> 📌 这与 H1 守卫是**同一个模式**：设备上限 ≤ 当前值 ⇒ 不替换、留痕、回落。
> H1 管的是「设备上限」维度，G6 管的是「设备行程」维度 ⇒ 两者可共用同一套守卫实现。
