## §0 方案一句话

**在「接口入参 → 推理输入」这一层，把接口放行但当前档数下无法解析的 8 个词（5/7 档独有词 4 个 + 编号轨越界词 4 个）降级到语义最近的合法 3 档，并留痕**；**不动**内核规则前件的严格解析语义。

> 📌 本质是**补齐一致性**：第 1 层（规则筛选）、第 2 层（建议去重）**已经在做**「5/7 档输入落到最接近的一档」，第 3 层（数值推理输入）漏了 ⇒ 本方案让三层对齐（详见 §3）。

## §3 为什么这是缺陷而不是设计（三层一致性论证）

**同一个「5/7 档词输入」的问题，项目在**两层**上都已经处理过，**唯独第三层漏了**：

| 层 | 代码位置 | 对 5/7 档词的既有处理 |
|---|---|---|
| 第 1 层：规则筛选 | `library/semantics.py::match_defect_name`（126-139） | **只比缺陷名、不比档位**。注释原文：「若此处仍按档位硬切…… 用户选『极轻微 / 极严重』时规则被**全部切光** ⇒ 对外报『无可用规则』」⇒ ✅ 已处理 |
| 第 2 层：建议去重 | `engine.py::_dedupe_advice_items`（1592-1597） | **按 μ 取最接近的那一档**，不按档位字符串精确匹配。注释原文：「用 μ 则是『取最接近的那一档』⇒ **5/7 档输入安全**」⇒ ✅ 已处理 |
| **第 3 层：数值推理输入** | **`engine.py::_build_defect_inputs`（1403）** | 直接 `level_to_domain_value` ⇒ 抛错被吞成 `None` ⇒ **缺陷维度整维掉出推理网络** ⇒ ❌ **未处理** |

⇒ 这**不是「新设计」，而是「既有兼容设计在第三层漏了」**：
前两层已经认定「5/7 档输入必须安全地落到最接近的一档」，第三层却让它**整维失活** ⇒ **三层行为不一致** ⇒ 缺陷。

另一条独立佐证：`specs.py:560-562` 的注释是一句**未兑现的承诺**：

> 「本表保留 5/7 档词：它是**接口入参**的合法词集合，收窄会让历史客户端直接 400，**而不是降级处理**。」

⇒ 接口层选择了「降级处理」这条路，但**算法层从未实现降级** ⇒ 实际行为是「比 400 更糟的第三种」：**静默失活**（请求成功、结果合理、就是少了缺陷相关的建议）。

| 代号 | 修法 | 位置 | 效果 | 代价 / 风险 |
|---|---|---|---|---|

## §5 推荐方案 D 的改动清单（2 个文件，3 处）

### 5.1 `fuzzy_core/macros.py`：新增降级口径函数（内核唯一口径处）

```python
def downgrade_level_word(lvl, level_word):
    """档位词在当前等级数下无法解析时，降级到语义最近的合法档位词。

    Returns:
        (词, 是否发生降级)
    """
```

**降级表（实测口径，覆盖接口放行的全部 8 个失活词）**：

| 轨道 | 入参词 | 3 档下映射 | 语义依据 |
|---|---|---|---|
| 语义轨 | `extremely_low` | `low` | 「极轻微」比「轻微」更低 ⇒ 3 档无更低档 ⇒ 取**保守**的 `low`（不夸大严重度） |
| 语义轨 | `very_low` | `low` | 同上 |
| 语义轨 | `very_high` | `high` | 「极严重」比「严重」更高 ⇒ 取保守的 `high` |
| 语义轨 | `extremely_high` | `high` | 同上 |
| 编号轨 | `level4` | `level3`（= `high`） | 「第 4 分位」在 3 档字段上不存在 ⇒ **钳位**到最高合法分位 ⇒ 与 `very_high→high` 同向 |
| 编号轨 | `level5` | `level3`（= `high`） | 同上 |
| 编号轨 | `level6` | `level3`（= `high`） | 同上 |
| 编号轨 | `level7` | `level3`（= `high`） | 同上 |

> ⚠️ **编号轨越界也必须降级**（初稿漏掉，经复核补上）：
> `ALL_LEVEL_WORDS` 含 `level1~level7` ⇒ 接口层**放行**且**主动展示**
> （`VALID_DEFECT_LEVEL_WORDS_TEXT` 里明写 `level1~level7`）⇒ 调用方
> 按提示填 `level4` 会撞上 `resolve_bucket` 的越界 `ValueError` ⇒ 与 `very_low`
> **完全同型**的静默失活。初稿只列了 4 个语义词 ⇒ **覆盖不全**。

实现要点：
- **先试 `resolve_bucket(lvl, word)`** —— 成功即原样返回（3 档词、`mid` 别名、合法编号 `level1~level3` 全部零影响）；
- 失败**且**该词在降级表里 ⇒ 映射后再试一次，成功则返回 `(映射词, True)`；
- 失败**且**不在降级表里（如 `'abc'`、`'严重'`）⇒ 返回 `(原词, False)`，**保持下游「不参与推理」的既有语义不变**；
- **降级表是「词的映射」而非「lvl 的映射」** ⇒ 同一张表在任意档数下都按「词的语义」降级（实测矩阵见下）：

  | 档数 | 降级的词 | 说明 |
  |---|---|---|
  | **3 档**（现网唯一档数，311/311） | **8 个**：语义轨 4 + 编号轨 4 | 本方案的完整覆盖面 |
  | 5 档 | 4 个：`extremely_low`/`extremely_high`/`level6`/`level7` | `extremely_*` 是 7 档独有词；`level6/7` 超出 5 档 |
  | 7 档 | **0 个** | 词表全覆盖，无需降级 |

  ⇒ 降级语义在任意档数下都成立（5 档下 `extremely_low → low` 同样是「保守」方向，`level6/7 → level5` 同样是钳位）；
  ⇒ 且**现网 311 条关键字全是 3 档** ⇒ 5/7 档路径**现网不会被触发**。

⚠️ **不动 `resolve_bucket` 本身**：规则前件解析保持严格（理由见 §4-C）。

### 5.2 `engine.py::_build_defect_inputs`：调用降级 + 留痕

```python
word, downgraded = downgrade_level_word(kp.lvl, level)
if downgraded:
    # 幂等：_build_defect_inputs 一次请求内会被调 2 次（数值层 + 去重层）
    key = ('LEVEL_DOWNGRADE', defect_name, level)

            'layer': 'numeric',
            'dimension': 'defect',
            'field': defect_name,
            'guard': 'LEVEL_DOWNGRADE',

            'lvl': kp.lvl,

value = level_to_domain_value(kp.lvl, word, kp.min_val, kp.max_val)
```

  - 该容器本来的定位就是「**字段定性降级清单**（每层一条）」⇒ `LEVEL_DOWNGRADE` 正好落在它的语义里；
- 缺陷位置名那处传的是 `'high'` 恒定值 ⇒ 天然不触发降级（可同样走该函数，行为不变）；
- ⚠️ **留痕必须幂等**：一次 `recommend()` 里 `_build_defect_inputs` 被调用 **2 次**
  （`engine.py:1454` 数值层、`engine.py:1613` 建议去重层）⇒ 直接 `append` 会产生**重复记录**
  ⇒ 需按 `(guard, field, from)` 去重（同一次请求内只留 1 条）。
- ✅ **下游无需同步改动**：`_advice_defect_mu`（1656）用的是**规则里写的档位**
  （`low`/`medium`/`high`）而非用户输入 ⇒ 对 3 档字段永远解析成功；
  且本项修好后 `defect_inputs` 里会有缺陷名 ⇒ 去重层从「`name not in defect_inputs`
  ⇒ μ 恒 1.0 ⇒ 取第一条」**自动恢复**为「按 μ 择优」⇒ **与 3 档行为一致**。

## §7 风险与边界

1. **降级是有损的**：`very_low` 与 `low` 在算法层**不可区分**。若业务真要区分「极轻微/轻微」，唯一出路是 §4-B（字段级 5/7 档）—— 但规则库 0 条 5/7 档词 ⇒ **收益近零，不建议做**。⇒ 本方案等于**正式承认「现网只有 3 档语义」**。
2. **降级会掩盖「用户填了非标准档位」** ⇒ 必须留痕（§5.2）⇒ **不得静默**。
3. **影响面是全部缺陷类规则**（不只 `MEL`）：改动虽只有 2 个文件，但回归面 = 缺陷反馈全链路 ⇒ 必须跑 §6 的 **8 条**口径。
4. **口径唯一性**：降级函数放 `macros.py`（内核口径处），**不要**在 `engine.py` 里另写一份映射表 ⇒ 避免两套真相源分叉。

---

## §8 回滚

- 改动集中在 `macros.py`（新增 1 个纯函数）+ `engine.py`（1 处调用 + 1 处留痕）⇒ **单点回滚**，无数据迁移、无 DB 改动；
- 若降级引发回归异常：把 `downgrade_level_word` 改为恒返回 `(原词, False)` 即可**一键回到现状行为**（缺陷维度照旧掉出网络）。
