## 1. 问题陈述

### 1.1 现象一：建议无优先级

一次短射反馈，模糊推理给出 8 个参数各自的调整建议。技术上每条都有规则依据，
但**没有「先保充填成形、再修缺陷」的排序** —— 充填量（`MEL`）与保压三件套（`PP0/PT0/PV0`）
被平级对待。

对照旧版：旧版有明确的优先级策略（§9 清单 C1~C4），新版**完全没有**。

### 1.2 现象二：参数集内部失配

`MEL`（**螺杆最终停放位置**）、`ML_N`（计量末段熔胶位置）、`DDAM`（**储后松退距离**）
是**三个不同的物理量**，但它们之间有确定的**物理关系**：

```
MEL = ML_N + DDAM
```

物理含义：注射成型像针筒一样 —— 计量到位后螺杆还要**回抽一点**避免熔胶流延 ⇒
螺杆最终停放位置比计量末段位置多出一个储后松退距离。

⚠️ 两个边界（易混，勿越）：

- **实际注射量 = `ML_N − VPTL`**（充填行程）；`DDAM` **不参与注射量计算**（螺杆回抽不吐料）；
- `DDBM`（前松退）净位移为 0，**不参与**上式。

规则库却把它们当作**三个平级的自由参数** —— 规则里甚至有
`IF BURN_low AND DDAM_worse THEN DDAM_reduce_2`，即单独调 `DDAM` 而不影响 `MEL`/`ML`。
规则推理完，三者的物理关系被破坏。

### 1.3 现象三：时间与速度独立调整 → 行程失控

`IT`（注射时间）与 `IV_n`（分段注射速度）满足 `行程 = 时间 × 速度`。
两条独立规则分别调整二者 ⇒ **有效注射行程被放大**，而充填量由 `MEL` 决定、不会跟着变。

> 实测（单段注射前提）：`IV0 35→39.13`、`IT 2.5→3.24`
> ⇒ 隐含行程 `35×2.5/4 = 21.9mm` → `39.13×3.24/4 = 31.7mm`（**+9.8mm**）
> ⇒ 同期 `MEL 357.62→360.79`（**仅 +3.17mm**）⇒ 差 6.6mm 的料 ⇒ 必然短射。

### 1.4 现象四：差值越限漏检

`over_limit.py` 的三个函数全部是「**单参数 vs 一个上限**」。但设备行程约束的是**位移**：

```
实际注射行程 = ML_N − VPTL
```

两个参数**各自都不超行程**，但**差值超行程** ⇒ 现检查漏网。
（`MEL ≤ 行程` 单独检查也过不了这一关。）

## 2. 三层划分

| 层 | 名称 | 输入 | 输出 | 语义 | 现状 |
|---|---|---|---|---|---|
| **L1** | 规则推理层 | 工艺参数当前值 + 缺陷反馈 | 候选调整意图（参数 + 增量 + 依据规则） | "这个缺陷，通常这样调" | ✅ 完备 |
| **L2** | 业务策略层 | 候选意图 + 业务上下文 | **定稿的意图**（保什么、先保什么、幅度多大、为什么） | "这一轮优先解决什么" | ⚠️ 只有地基（§4.1） |
| **L3** | **锚点层** | 被改动的量 + 工艺参数集 | **锚点关系成立**的参数集 | "这个量变了，哪些量要跟着变" | ⚠️ 只有一元部分（§4.3） |

> **L3 = 信息锚点**（用户口径，2026-11 拍板）：每个派生量都有明确的**锚** —— 它由谁算出来。
> 参照系是**注塑机的行为**：界面上 `MEL` 本身就是自动计算值（改 `ML` 或 `DDAM` ⇒ `MEL` 自动变），
> 我们参数集里保留 `MEL` 只是为了存和用；**L3 是在复现这个自动计算机制**。
> ⇒ **与改动来自手工编辑还是规则优化无关** —— 两种来源共用同一套锚点传导。
>
> **参数检查不属于这三层**：它是**通用能力**（对工艺参数看现状，任何时候可跑），
> 落点 `backend/process/algorithms/check_params.py`（与第3层 `integrate_params.py` 平级）。
> 检查与推理**共用同一批字段口径与锚点关系**，只是两个用法：
>
> | 用法 | 输入 | 输出 | 归属 |
> |---|---|---|---|
> | **传导** | 改了哪些 + 参数集 | 连带算出来的参数集（**改值**） | L3 |
> | **自检** | 只有参数集 | 哪里锚点不成立（**不改值**） | 检查层 |
>
> **写入前的收口**（批次 6）：`backend/process/algorithms/param_consistency.py`
> —— 落点是「**参数集落库前**」，**不认写入来源**（用户口径：只对数据负责，
> 手工编辑与规则优化共用同一套）；它把上面两个用法串起来：差分出「改了哪些」
> ⇒ 传导 ⇒ 回填 ⇒ 自检（详见 §8.4.2）。
> （**批次 9 已重排** ⇒ 落点改为 `algorithms/integrate_params.py::integrate`（第3层）
> + `algorithms/check_params.py::validate`（第4层）。）

### 2.1 为什么是这个顺序

**一致性约束是「实现层」，它不应改变「意图」。**

- "把储料终止位置调到 360.79" = **意图**
- "ML 末段必须同步变成 357.29" = **把意图翻译成自洽参数集的实现约束**

反之不成立：若一致性先跑，它会把意图**改掉**（`MEL` 被裁剪、`IV` 被拉回），
而"该保充填还是该修缺陷"这个决定还没做 —— 顺序就乱了。

⇒ **先定意图（L2），再实现意图（L3）。**

### 2.1.1 L3 的触发条件：这次改动有没有连带影响

L3 **不是**「一轮改了很多参数才需要」—— 那是 L1/L2 的场景特征，不是 L3 的触发条件。
L3 的触发条件只有一个：**这次改动按锚点关系会不会引发其它量变更**。

| 情形 | 是否触发 L3 |
|---|---|
| 一次命中 8 条规则、改 8 个量，但互不耦合 | 逐个判断 ⇒ 该联动的联动，不耦合的不动 |
| 只改 1 个量，但它有连带影响（`MEL` ⇒ `ML_N`） | **照样触发** |
| 改了量，但没有任何锚点关系牵连 | 不触发 |

⇒ 粒度是**逐个被改的量**（`propagate` 的 `direct` 里每个 key 各自传导），
不是「一轮改一堆 ⇒ 一起补」。
⇒ 手工编辑与规则优化**共用**这一套传导（参照系是注塑机行为，不是「谁触发的」）。

### 2.2 旧版佐证

旧版 `tsk_algorithm` + `process_optimize_service` 的实际执行顺序，恰好就是这三层：

| 旧版步骤 | 对应层 |
|---|---|
| `model.predict(top_k=10)` → 候选规则 | L1 |
| 缺陷列表 `break` 取第一个 / `SHORTSHOT`+`MEL` 置顶 / `w` 幅度系数 | **L2**（混在 L1 里，未分家） |
| 应用增量 → `MEL` 特殊处理 → 料筒温度链 → `IL` 倒推 | **L3** |
| `param_check` 截断 | L3 的可行性部分 |

旧版的毛病**不是顺序错**，而是 **L2 糊在 L1 里、L3 散成 if-else**。

## 3. 核心概念：同步组（Synchronization Group）

### 3.1 取消「主控 / 从属」

初版设计曾引入"主控参数"概念（如"`MEL` 主控、`ML` 跟随"）。**该模型是错的**：
`MEL` 与 `ML_N` 是**两个不同的物理量**（螺杆最终停放位置 vs 计量末段熔胶位置），
二者之间是**确定的物理关系** `MEL = ML_N + DDAM` —— 既不是谁主谁从，也不是同一量的两种说法。

正确表述：

> **同步组** = 一组由恒等式绑定、必须同时成立的参数。
> 当组内**任一量**被改动，其余量按定义**重新推导**（而不是"从属跟随某个固定主控"）。

### 3.2 自由度的选择 = 被改动的那个量

等式约束 + 一个自由度 ⇒ 求解方式：**谁被直接改动，谁就是当次的自由度**，其余由恒等式推出。

| 规则改的是 | 推导方向（**业务口径**） |
|---|---|
| `MEL`（计量终止位置） | 推出 `ML_N = MEL − DDAM`（**末段**；只含后松退） |
| `ML_N`（末段熔胶位置） | 推出 `MEL = ML_N + DDAM` |
| `DDAM`（后松退距离） | 推出 `MEL = ML_N + DDAM` |
| `DDBM`（前松退距离） | **不联动** —— 前松退不影响计量终止位置 |
| 任一段 `ML_i`（多段） | **各自独立**，直接生效；只校验「严格递增 + 首段 > `VPTL`」，违反 ⇒ 该直接改动**回退** + 留痕 |

> 本表用**算法/工艺侧**命名（`MEL` / `ML_N` / `DDAM` / `DDBM` / `VPTL`）；
> 与代码字段名的对照见 §6。

⇒ **双向**，不存在主控。

### 3.3 有序传播

同步组内的传播**有顺序**，不是一次性投影。旧版的链条是：

```
MEL → ML_N → d 表重排 ML_1..N-1 → IL_倒推 → VPTL
```

⇒ L3 需要**按序联动**（改 `ML_N` 影响 `IL_0`，`IL_0` 又影响别的 —— 顺序错了就错）。
实现上采用「**一条规则一个函数**」的直白结构 + 规则清单（`LINK_RULES`），
而不是通用等式求解器 —— 规则数量不多、每条都能一句话说清时，通用框架反而更难读。

### 3.4 冗余量（余量）

**物理定义**：补缩量 = 收缩 + PVT 压缩。充填完成后螺杆必须后退这段距离来补缩，
这段位移**不产生充填**，是必须预留的。

| | 旧版 | 新版 |
|---|---|---|
| 计算方式 | `length_ratio` 按**制品重量档**取固定值：`≤50g→0.85` / `50~100g→0.90` / `>100g→0.95` | **由物理反推**：`replenish_len = (shrink_rate + pvt_compress) × weight / (melt_density × a_screw) × 1000`，`length_ratio = 1 − replenish_len / total_len` |
| 出处 | `process_generate.py:262-274` | `expert/algorithm_engine.py:2024-2053` |
| 覆盖 | 固定档，粗糙 | 物理自洽，**优于旧版** |

⚠️ **缺口**：新版冗余量只用在**初值推导**里。调整之后，**没有任何机制保证新的注射行程
仍保留同一份余量口径**。⇒ L3 重算行程时必须显式携带该余量。

### 3.5 设备设定值不等于实际值

注塑机设定值与真实值存在偏差（螺杆磨损、液压漂移、温度耦合）。
⇒ **计算必须依据一个明确的物理基准**，否则无法判断"算得对不对"。

⇒ 口径：L3 一律以**理论物理量**（充填量、体积、行程）为基准计算，
   不以机台反馈值为基准；实际偏差留给现场闭环（实测反馈）消化。
   **这条决定了 §8.3 的"锁行程"选型 —— 见 §5.1。**

## 5. 已确认决策

### D1. 注射时间 ↔ 速度 ↔ 行程：**锁行程**

| | 内容 |
|---|---|
| 决策 | 以**注射行程**为不变量，调整速度或时间时，行程保持不变 |
| 理由 | 充填量由产品决定 ⇒ 行程属**不可动量**；改行程 = 改充填量 = 改需求 |
| 配套 | ①锁行程 ⇒ 速度与时间**互为倒数**，二者只能取其一为自由度<br>②设定值≠实际值 ⇒ 基准必须是**理论物理量**（行程），不是机台反馈值（§3.5）<br>③余量口径必须随行程一同携带（§3.4） |
| 推论 | ①规则里 `IV1_add_8` 与 `IT_add_0.75` **不能同时生效** —— 二者互相矛盾，必须择一或按行程反解<br>②**行程增量的换算**：位移增 `ΔL`、速度不变 ⇒ 时间增 `Δt = ΔL / v`<br>⚠️ 旧版 `process_optimize_service.py:945` 是 `IDT_main += ΔMEL` —— **把 mm 直接加到 s 上，单位混用**，迁移时必须修正为 `Δt = ΔL / v`<br>③余量口径必须随行程一同携带（§3.4）<br>④**自由度 = 速度**（已拍板）：注射阶段实际是**速度控制**，设定时间只是设定值（实际时间与设定值有偏差）⇒ 速度是主控量、**时间是从属量**；规则命中时间类建议而速度有值时，该建议被速度的自由度取代（留痕 `superseded` 且**值回退** = 让位不生效）<br>⚠️ **批次 2 修正**：新版 expert 的 `inj_t` 是「几何下限 + 工艺窗口钳制」的结果（`algorithm_engine.py:2122`），且用的是**设备最大速度 × 填充效率**而非设定速度 `inj_spd_1` ⇒ 「时间 = 行程 ÷ 速度」在新版**不是恒等式** ⇒ G3 降级为**窗口校验**（改速度不联动时间） |

### D2. `MEL` / `ML` 双向同步，无主控

见 §3.1 / §3.2。同步组内，谁被改动谁就是当次自由度，其余按恒等式推导。

### D3. 超行程处置：**分级调整 + 冗余量**，不是直接截断/拒绝

用户口径：`MEL − VPTL` 是实际注射行程；若联动后 `MEL` 超行程，
**可以调整 `VPTL`**（VP 切换位置 = 注射终点位置），但对应的 `IL` / `ML` / `MEL` 都要跟着调，
**并且需要一层冗余量**（不能压到底）。

处置链（待细化，见 §8.3）：

```
联动后 MEL > 设备最大注射行程
   ↓
① 可否下调 VPTL 腾出空间？（VPTL 下移 ⇒ 注射终点提前 ⇒ 行程变短）
   │   否
   ↓
② 下调 VPTL 后仍需保留冗余量（补缩量）—— 余量不足 ⇒ 不允许压到底
   │   仍不足
   ↓
③ 超出设备物理能力 ⇒ 400 拒绝（产品在这台机做不出来 ⇒ 换机）
```

⚠️ **注意**：现状的 `over_limit.py` 是「`MEL` 单独比行程」，与本链**不是同一件事**：
本链处理的是「**联动后**的参数集是否还装得下」，且允许通过调 `VPTL` 换取空间。

### D4. 落点与顺序

- 落点：`algorithms/` 根层（§4.4）
- 顺序：**先 L3 后 L2**（§10）—— L3 不做时，L2 的优先级判断是在一堆非法参数上做的

## 6. 位置类量的物理定义（必须先统一）

新旧字段名对照与恒等式：

| 量 | 算法名 | 业务字段 | 定义 | 关系 |
|---|---|---|---|---|
| 储料终止位置 | `MEL` | `met_end_pos` | 计量完成、螺杆后退到位的储料位置；**自动计算量**（机台上由 `ML_N + DDAM` 算出） | `MEL = ML_N + DDAM`（**只含后松退**） |
| 末段熔胶位置 | `ML_N` | `met_pos_N` | 计量到位的最后位置 | 同上 |
| 熔胶前松退距离 | `DDBM` | `pre_met_decomp_dist` | 计量前螺杆后退量 | — |
| 熔胶后松退距离 | `DDAM` | `pst_met_decomp_dist` | 计量后螺杆后退量（防熔胶流延） | — |
| 补缩量 | — | `replenish_len`（**派生量**，不落库） | 材料收缩 + PVT 压缩需要的额外推进量 | **只在 expert 基准计算出现**（定 `total_len`/`inj_len`/`vps_pos`）；**不进 L3、不参与优化** |
| VP 切换位置 | `VPTL` | `vps_pos` | 注射终点 / 保压起点位置 | **实际注射行程 = `ML_N − VPTL`** |
| 一段注射位置 | `IL_0` | `inj_pos_1` | 注射起点位置 | `IL_i = MEL − Σ IDT`（倒推） |
| 注射时间 | `IT` | `inj_t` | 总注射时间 | `行程 = IT × 速度`（单段时 `IT = 4×行程/速度`） |

### ✅ 定义佐证：旧版初始化公式自洽

旧版两个初值公式互相印证（`process_generate.py`）：

```
306: VP_swit_posi = base_posi + (1 - length_ratio) * injection_length
483: meter_posi   = base_posi + injection_length
```

⇒ `ML_N − VPTL = ratio × injection_length = 实际注射行程` ✅
⇒ 「**实际注射行程 = `ML_N − VPTL`**」在旧版已自洽成立，可直接作为 L3 的物理基准。

### ⚠️ 定义澄清：`MEL − VPTL` ≠ 实际注射行程

- **实际注射行程 = `ML_N − VPTL`**（螺杆从 VP 位置退到计量末段位）
- `MEL − VPTL = 实际注射行程 + DDAM`（**含后松退量**）

旧版代码用的是前者（`process_optimize_service.py:915-917`：
`act_inject_lenth = ML_{meter_stage-1} − VPTL`）。

⇒ 文档与实现统一采用 **`ML_N − VPTL`**；`MEL − VPTL` 仅在需要含松退量的场合使用。

### ⚠️ 差值越限（新发现的检查缺口）

设备行程约束的是**位移**，而非单个位置：

```
ML_N − VPTL ≤ max_injection_stroke
MEL       ≤ max_injection_stroke
```

`over_limit.py` 逐参数比较，**差值这一条漏检**。
⇒ L3 需补一条**组内差值越限**检查（§8.2）。

## 7. L2 业务策略层设计

### 7.0 实现红线：L2 是「机制」，不是「业务知识」

本项目既有原则（`development_practice_specification`：规则库渐进生长）明确：
**工艺判断不得以 if-else 固化在代码里** ⇒ 「新增经验 = 改代码发版」。

⇒ **L2 提供的是机制**（策略接口、优先级裁决、让位、留痕），
**具体业务优先级规则必须是数据**（规则库中的规则 + 派生输入量表）。

| 内容 | 落法 | 可否写成代码 |
|---|---|---|
| 「短射 + 重量不足 ⇒ 充填优先」 | **派生输入量表**（把「重量不足」做成可注册的派生量）+ 规则库中的排序/激活规则 | ❌ 不可写成 `if defect == 'SHORTSHOT' and ...` |
| 「充填优先于保压」这条**次序本身** | L2 的优先级机制 + 数据化的优先级表 | ❌ 不可硬编码次序 |
| `MEL = ML_N + DDAM` | L3 领域层（物理恒等式） | ✅ 可以（见下方末注） |

⚠️ **末注（关键区分）**：L3 **不违反**「规则渐进生长」原则 ——
因为它不是「随经验增长的知识」，而是**锚点关系 = 注塑机的既有行为**
（界面上 `MEL` 就是自动算的，改 `ML`/`DDAM` 它就变）。
用既有口诀区分：**逻辑（解释规则的方式）固定，规则（知识本体）可增长** ——
锚点传导属于「逻辑」⇒ 固定在领域层代码；工艺经验属于「知识」⇒ 必须落数据。

⚠️ **旧论证作废**：早前把这条论证写成「L3 是物理恒等式（恒真的约束）」—— **站不住**：
恒真的约束应当任何时候都成立（初始化、手工编辑时也成立），那它就不该是"L3 的一步"。
真正的区别是**它在流程中的位置**：L3 处理的是「已定意图 → 自洽参数集」的**执行翻译**，属「逻辑」侧。

⚠️ 旧版对照：`process_optimize_service.py:666-673` 正是 `if target_defect == "SHORTSHOT" and actual_product_weight < product_weight` 的硬编码 ⇒ **照搬即违规**，其正确迁移形态是 §7.2 的数据落法。

### 7.1 缺陷选取（口径已定 = 阶段序）

**接入点**：`defect_selection.select_defect(feedback)`（**唯一入口**，口径固定，无策略入参）。

| 策略 | 何时用 | 行为 |
|---|---|---|
| `stage_priority`（**当前唯一实现**） | 默认 | 按调机阶段重排后取第一个有效缺陷（打足 → 补缩 → 外观） |
| **待新增：充填优先** | 存在"成型性"缺陷且有实测重量反馈 | 见 §7.2 |

⚠️ **现状更新（2026-11-19）** —— `first_valid` / `first_only` 两个占位口径
**已删除**（前者是早期为跑通流程设计的占位实现，后者与「只取首个」重复）；
⚠️ **「策略切换」机制一并删除**（Protocol + `strategy` 形参）—— 当前用不到，
按「用不到就不写代码」原则不留空壳；将来真有第二个口径时再加回。

⚠️ 新增策略**不得改变** `stage_priority` 的既有行为（它是当前默认口径）；
⚠️ 换默认策略属口径变更，需用户拍板。

⚠️ 新策略的**规则内容**仍受 §7.0 约束：策略实现只负责「按数据裁决」，
具体缺陷优先级规则应来自规则库 / 派生输入，而非写在策略类的 `if` 里。

### 7.2 充填优先策略（旧版 C1/C2 的迁移）

**触发条件**（旧版口径，**但实现必须走 §7.0 的数据落法**）：

```
目标缺陷 = 短射（SHORTSHOT）
  且 反馈实际制品重量 存在
  且 实际重量 < 目标重量
```

⇒ 「重量不足」需先做成**派生输入量表**中的可注册派生量
   （例如「充填达成率 = 实测重量 / 目标重量」），再由规则库中的规则引用它；
   **不得**在 L2 代码里直接写 `actual_product_weight < product_weight`。

**行为**：

1. **充填优先于缺陷修正** —— 涉及充填量的参数（`MEL` 及其联动量）优先，
   保压/缺陷类参数让位；
2. **`MEL` 不走规则增量**，改按重量比例重算注射行程：

```
rec_inject_lenth = product_weight × act_inject_lenth / actual_product_weight
```

（`act_inject_lenth` = `ML_N − VPTL`，旧版 `process_optimize_service.py:915-926`）

3. **决策必须留痕**（§7.5）。

### 7.3 参数优先级与让位

L2 的第二职责：给候选意图**排序 / 裁剪**。

- 建议顺序：**充填相关（`MEL` / `IL` / `IV` / `IT`） → 保压相关（`PP`/`PV`/`PT`） → 其他**
- 让位规则：若充填相关参数已满足目标（例如实测重量达标），
  保压类建议才进入最终集合
- ⚠️ **让位必须是显式决策 + 留痕**，不能静默丢弃（否则用户看到"少了几条建议"无从追溯）

⚠️ **两类“不可调”要分开**（**12.4a 已落地**，机制在 `algorithms/decide_direction.py`）：

| 机制 | 字段 | 含义 | 留痕理由 |
|---|---|---|---|
| **白名单** | `allowed_params`（空 = 不限制） | **场景范围** —— 这个场景该动哪些旋钮 | 「本场景不允许」 |
| **禁入清单** | `blocked_params`（空 = 不禁） | **基线项** —— 任何场景都不该动的旋钮 | 「基线项 ⇒ 不参与阶段调机」 |

⇒ 两者都作用在候选的**业务字段名**上；**禁入排在准入之前** ⇒ 同时命中时留痕写“基线项”
（全局理由更强）。⇒ 基线项只需写**少量字面量**（注射速度 6 项），
不需要列“所有可调旋钮”全集。

### 7.4 幅度系数（已有，不重复造）

缺陷程度 → 调整幅度，新版已有 `trend_to_factor` / `adjustment_factor`。
旧版的硬编码表（`w`：0.9→2.1 / 0.8→1.9 / 0.5→1.5 / else→1.0）作为口径参照。

### ⚠️ 疑似缺陷：expert 多段计量重复计入 `replenish_len`（**未修**）

**现象**：expert 多段计量的末段位置比储料到位位置 `meter_posi` 多出一个 `replenish_len`。

```
vps_pos    = cushion_len + replenish_len      # :2047 inj_pos → :2182 vps_pos
meter_posi = cushion_len + total_len           # :2387 储料到位位置（单段计量终点）
met_pos_i  = vps_pos + coef_i × total_len      # :2839 多段分配（现状）
⇒ met_pos_N = cushion_len + replenish_len + total_len = meter_posi + replenish_len   # 多算一次
```

**根因**（业务口径）：`replenish_len`（补缩量 = 收缩 + PVT 压缩）是在**基准运算**阶段
（`:2034`）算出来的，且 `inj_len = total_len − replenish_len`（`:2037-2038`）已经把补缩量
**扣除**过一次 ⇒ **分配阶段不该再计入**（前面已经考虑过了）。

**正确式**（分配跨度 = 充填行程 = `total_len − replenish_len` = `inj_len`）：

```
met_pos_i = vps_pos + coef_i × inj_len
⇒ met_pos_N = vps_pos + inj_len = cushion_len + total_len = meter_posi   ✅ 闭合
```

⇒ 现状是末段**退过头**（超过储料到位位置），并让 expert 的 `MEL` 与 `ML_N` 差 `replenish_len`。

**处置**：⚠️ **未修** —— 改 expert 会改变多段计量的既有输出 ⇒ 待用户拍板；
L3 侧按**业务口径**（`MEL = ML_N + DDAM`）实现，单段时与 expert 无差异。

### 8.2.1 锚点关系自检（补缺）

⇒ **容差**：位置类关系允许偏差 **0.01 mm**（远小于任何物理失配量级）。

### 8.4.1 谁说了算：自动计算量 vs 独立量

L3 = 信息锚点 ⇒ 每个量要么是**独立量**（自己说了算），要么是**自动计算量**
（由锚点关系算出来）。**不存在「手工优先」这种全局规则** —— 要先看改的是哪一类：

| 改的是 | 处置 | 为什么 |
|---|---|---|
| **独立量**（`ML_N`、`DDAM`、各段 `met_pos_i`） | 生效，并按锚点关系联动更新自动计算量 | 它自己没有上游，是这个量的锚 |
| **自动计算量**（`MEL`） | **先定 ML，再由 ML 确定 MEL**（MEL 目标 ⇒ 解出 `ML_N`），最终值仍等于用户填的值 | `MEL` 是算法侧的**标**；机台上真正会被调的是计量位置与储后松退 ⇒ 目标先落成决策量，终止位置再由它算出（前端「终止位置」**只读**） |
| **两端同时改**（`MEL` 与 `ML_N` 都改） | **自动计算量优先** —— 以独立量（`ML_N`）为准**重算** `MEL` + `conflicts` 留痕 | 两个要求同时成立时无解；但 `MEL` 是派生量 ⇒ 它不与上游争，取「派生量让位」的那个（用户口径，2026-11-12） |
| 违反硬约束（如回抽链非递增） | 该直接改动**回退** + 留痕 | 硬约束不是优先级问题，是物理不成立 |

> ⚠️ **旧的「手工优先 + 提示」提法作废**：那是把「自动计算量」当成可与上游平起平坐的
> 独立输入。在机台上没有这个选项 —— `MEL` 的值由 `ML_N + DDAM` 决定，
> 用户改 `MEL` 必然带动上游。

> 代码侧：规则清单 `LinkRule.auto_field` 显式声明每条规则的**自动计算侧**
> （空串 = 两侧各自独立）⇒ G1 = `met_end_pos`；G2 / G3 无自动计算侧。

> **「先定 ML，再确定 MEL」**（用户口径，2026-11-12）：两端算的是**同一条等式**
> （`MEL = ML_N + DDAM`），区别只在**谁先被确定**。统一按「先定 ML」走：
>
> - **算法 / 接口给来 MEL 目标** ⇒ 先翻成**决策量**（`ML_N = MEL − DDAM`），
>   `MEL` 再由 `ML_N` 算出（`anchors.resolve_mel_target` →
>   `direction.apply_mel_targets`）；
> - **前端「终止位置」只读** ⇒ 用户改的是计量位置与储后松退，终止位置自动跟着变
>   （很多注塑机界面本就没有 MEL 这个量 ⇒ 用户改 MEL 的场景不确定，
>   而 ML / DDAM 的行为是确定的）。
>
> ⚠️ 旧版迁移清单 B1「`MEL` 改 ⇒ 重算 `ML_N`」的**算式没变、逻辑变了**：
> 现在不是「拿 MEL 去覆盖 ML」，而是「拿 MEL 目标先定 ML，再由 ML 定 MEL」。
>
> **推算只用「旧值 + 调整量」**（用户口径，2026-11-12）：L3 手里没有「新值」
> 这个概念，只有**旧值**（现状参数集）与**调整量**（L2 / 规则传过来的）⇒ 两步式：
>
> ```text
> ① ML_N 基准 = 原MEL − 原DDAM
> ② MEL_新    = ML_N + DDAM + ΔDDAM + ΔMEL
> ```
>
> ⇒ 落库的计量位置 = `原ML_N + ΔMEL`：**`ΔDDAM` 不叠加到计量位置**，它落在
> `MEL` 那一侧（终止位置随松退距离自然后移）；`MEL` 再由 `ML_N + DDAM` 算出。
> 能不能同调是**歧义消解** ⇒ 归 **L2**（定「调哪个、谁让位」）。

### 8.4.2 写入前的收口：谁写的都一样

用户口径（2026-11-12）：「**不区分优化还是手工，只对数据负责**」
⇒ 收口点不按**调用来源**分叉，而定在「**参数集落库前**」。

| 写入路径 | 入口 | 旧值从哪来 | 收口做什么 |
|---|---|---|---|
| 手工编辑 | `services/parameter.py::update_parameter` | 数据库里的当前值 | 差分 ⇒ 传导 ⇒ 回填 |
| 规则优化产出 | `services/parameter_optimize.py::_create_new_round` | 父轮次 | 差分（= 推荐改的量）⇒ 传导 |
| 初始化（新建轮次） | `services/parameter_initialize.py::_create_process_parameter` | **没有** | 只自检（值由算法产出，本应自洽） |
| 克隆 / 复制 | `parameter.py::clone_round_from_parameter`、`parameter_initialize.py::_copy_process_parameter` | 源轮次 | 原样复制 ⇒ 无改动 ⇒ 只自检 |

**为什么需要「差分」**：写入方给的都是**整份参数**（手工编辑提交全量字段；
优化给的是「基线 + 推荐覆盖」），而传导层要的是「这次改动了哪些量」。
⇒ 有旧值可比 ⇒ 差分得出；没有旧值 ⇒ **不臆造改动**，只做自检。

**代码落点**：`algorithms/integrate_params.py::integrate(values, previous)`
（第3层；差分 → `integrate_params.propagate` 传导 → **按差异回填**。
自检已拆到第4层 `check_params.validate`。）
按差异回填是刻意的：联动推导、让位回退、硬约束回退、冲突时的「自动计算量优先」
重算，都会体现为「与新值不同」⇒ 一条回填规则覆盖四种情形，且不碰无关字段。

**留痕**：先只落**后端日志**（`direct` / `derived` / `superseded` / `conflicts` /
`unresolved` / `violations`）—— 不动接口响应契约，前端本期不展示。

### 8.4.3 L2 裁决：落地链路上的位置

规则推理（L1）给出的候选调整是**平级**的（每个缺陷推出一批），
「同一批里能不能同时调两个量 / 谁让位」是**歧义消解** ⇒ 归 **L2**。

**落地链路**（`algorithms/decide_direction.py::resolve_direction` → `algorithms/integrate_params.py::apply_direction`）：

> ```text
> 算法建议 ─①候选集─▶ ─②L2 裁决─▶ ─③执行保留项─▶ ─④L3 传导─▶ 参数集
>              （只筛"不算建议"的）  （谁让位/暂缓）  （MEL 先收集）  （MEL ⇒ ML_N）
> ```

> ⚠️ **② 必须先于 ④**：若 L2 在 MEL 翻译**之后**，它只看得到「调计量位置」，
> 看不见 MEL 的意图 ⇒「调 MEL 时不许同时调 DDAM」这类规则就无处安放。

> ⚠️ **批次 12.8：② 多一道「本轮落不了地」的排除**（让位对象不可调 ⇒ 本量改了也
> 白改 ⇒ 不能占名额）。物理关系在**底座**（`algorithms/anchors.py::FREEDOM_YIELDS`
> / `unlandable_params`），第2层只读不改 ⇒ 两层不各自持一份真相。
> ⇒ 少了这一步就会发生「L2 选了 `inj_t` → L3 的 G3 让位把它回退 → **本轮零变化**，

> ⇒ 不为单个字段在第2层做兜底）：**「本机有没有这个字段」「会不会白改」都归第3层校验**

  - 业务口径参照：注射阶段是**速度控制** ⇒ 改速度不动时间；改时间则让位给速度
  - 业务口径参照：工艺窗口是经验区间 ⇒ 越界可检出（注射时间 / **各段保压时间**）
  - 业务口径参照：多段保压各自设定 ⇒ 改一段不动另一段（系数只属初始化，与 G2 同口径）
  - 小数位参照：位置/时间 **2 位**、压力/速度 **0 位**（与 `_format_output` 一致）
