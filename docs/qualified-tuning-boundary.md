# 合格态调机（经济性调机）· 功能边界设计

> **目的**：把「产品已合格之后还能省什么、这一层归谁管」划成**明确边界**，
> 让后续实现有据可依，且**不破坏现有 L1–L4 分层**。
>
> **状态**：**已落地**（2026-11-25，批次 15.1）—— 落法与初版设计**不同**：
> **不新建 L1 引擎、不新判据源** ⇒ 复用现有分层，只在**调机策略**里补一条
> 「合格态」策略（候选由场景自带，目标值由新口径 `step_down` 解算）。
> **口径初值已落地**（递减步进 + 5% 步长），**标定仍待实测**（见 §6）。
>

## 0. 定位：一句话

> **缺陷修完之后，产品已合格 ⇒ 还能省能耗（压力）、省周期（时间）。**
> 这件事属于**调机逻辑**，但它**不由缺陷驱动**，而由**实测观测 + 试模反馈**驱动。

用户原话（本轮）：

> 合格态下的产品，可能会有周期/能耗方面的要求，比如说我 70MPa 的压力就可以将产品打好，
> 我就不需要 80MPa，浪费能耗；如果 20s 就能打出产品，就不需要 25s，
> 这是合格态下的逻辑，这部分可能还是属于调机逻辑部分的，因为 fuzzy 只处理缺陷部分的。

⇒ 三层含义：

1. **合格态不是终点**，是**第二阶段调机**的起点（第一阶段=修缺陷，第二阶段=降能耗/降周期）。
2. **不在 L1 找答案** —— fuzzy 只处理缺陷，合格态没有缺陷 ⇒ fuzzy 零产出。
3. **仍在调机逻辑的分层内** —— 分层不换。

⚠️ **2026-11-25 修正**：本文初版把第 2 条写成「**需要第二个判据源**」—— **已作废**。
批次 15.1 的落法是**不新判据源、不新建引擎** ⇒ 判据仍是 **`feedback.tuning_result`**
（合格与否**只由反馈说了算**，**不能拿「引擎有没有产出」反推合格**）；
真正缺的是**候选来源**与**目标值来源** ⇒ 分别由「场景自带候选」与「口径解算」补齐。

## 1. 合格态没有缺陷 ⇒ 缺陷驱动引擎全部沉默（**事实**）

| 事实 | 证据 |
|---|---|
| fuzzy 的触发源是**缺陷码** | `is_available` 里 `if not self._extract_defect_context(context): return False`（`fuzzy/engine.py` L463） |
| 合格态 ⇒ 无缺陷 ⇒ fuzzy **零产出** | 同上 |
| 合格态时**三个现有引擎全部沉默** | llm：`is_available` 恒 `False`（`llm_algorithm.py` L58）；empirical：无缺陷即 `False`（`empirical_algorithm.py` L167）**且它本身不给数值**（`recommended_value=None`，L130/L147）；fuzzy：见上 |
| 「省能耗/省周期」**不是缺陷**，是**约束优化** | 规则原料 §6 明写「周期」在项目里**没有缺陷码**，只作全局约束 |

⇒ **候选（调哪个旋钮）没有来源** —— 而第2层的场景策略**只产「调哪个 +
什么口径」，不产建议值** ⇒ 光加一条场景策略仍然落不了地。

⇒ **落法（2026-11-25 定案）**：**不新建引擎、不新判据源**，复用现有分层 ——

```
        ┌─ 缺陷源（现有） ── 缺陷码 → fuzzy 规则 → 加/减 → 修缺陷
输入 ───┤
        └─ 合格态（新增） ── 合格判据 → **场景自带候选** → 口径解算 → 降 → 省能耗/省周期
```

**候选从哪来** = 场景策略自己声明（`candidate_params`）；
**目标值从哪来** = 第3层按口径解算（`step_down` = 递减步进）。
⇒ 两条源**不同时发声**（缺陷态 ⇒ 合格态策略不命中；合格态 ⇒ 缺陷策略不命中），
⇒ **判据唯一**这条分层铁律仍然成立。

## 3. 分层落点（与现有分层不冲突）

### 3.1 L1：**不动**（不需要新引擎）

- 现有三个引擎在合格态全部沉默（§1）⇒ **合格态路径不走 L1**。
- ⇒ **不新建平级引擎**（初版设计作废）—— 新引擎只会把「判据源分离」
  变成**两套引擎体系**，与「用不到就不写代码」相违。

### 3.2 L2：新增场景「合格态省能耗」（**已落地**）

| 项 | 内容 |
|---|---|
| 落位 | `services/optimize_chain/decide_adjustment.py::SCENARIO_STRATEGIES`（新增 `qualified_efficiency`，`priority=5`） |
| 触发条件位 | **事实表**的 `last_tuning_result`（**已有**：`decide_adjustment.py::collect_facts` 已从 `feedback.tuning_result` 填入）⇒ **合格态即一个场景，零新机制** |
| **自带候选** | `candidate_params=('inj_pres_1',)` —— **新增能力**：算法零产出时仍能有调机对象（`decide_adjustment.py::ScenarioStrategy`） |
| 声明物 | `allowed_params` / `preferred_params` / `max_items=1`（U-01「一次只改一个量」）/ `target_modes={'inj_pres_1': 'step_down'}` |
| **不做** | 不自己算目标值（铁律：L2 不读参数集 ⇒ 算不出目标值）；**不产建议值** |

### 3.3 L3：新增口径「递减步进」（**已落地**）

- 现有 `fill_ratio` 口径是**充填量比例**解算注射行程，**不适用于**经济性。
- ⇒ 新增 `step_down`（`anchors.py`）：**目标 = 当前设定 × (1 − 步长)**。
  - **不依赖物理模型** —— 「上一模合格」只说明当前设定够用，**不说明能降到哪**
    ⇒ 只能小步试探，靠试模反馈逼近够用线。
  - 步长初值 **5%**（`anchors.STEP_DOWN_RATIO`）—— **初值不是结论**，待实测标定。
- `apply_scheme` 从「只对 `met_end_pos` 走口径」**推广为逐字段按口径**（口径比算法给的
  绝对值更具体 ⇒ 口径优先）。

### 3.4 观测数据边界

| 项 | 现状 |
|---|---|
| 契约 | **已有 4 键，零改动**（`schemas/optimization.py` L56-68 `CycleObservationSchema`） |
| 前端 | **已能采集上报**（`frontend/src/constants/observation-order.ts` L19-23，带单位 weight/pressure/time） |
| 后端消费 | 目前**只有 `actual_product_weight` 有消费方**（`read_weights`，anchors 底座）；其余 3 键零消费 |
| 接法 | 多取 3 键 ⇒ 进**事实表**（决策层入口 `collect_facts` 挑料）⇒ 场景条件可引用**任意键**、L1 引擎可读（**纯数据接线，零行为变化**） |
| **边界** | 观测值**只作事实输入**，**不作目标值** —— 「实测 70」与「目标该设多少」是两个问题（§6 R1） |
