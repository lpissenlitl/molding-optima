> **目的**：本对话积累了大量设计决策，需要在新对话开启"优化之旅"前归档。
> **作者**：与用户 2026-09-03 多轮对话整理

## 一、核心架构定位

### 1.1 双模架构（可独立可嵌入）

molding-optima = 一个可独立可嵌入 molding-expert 的应用模块：

| 运行模式 | 部署 | 数据库 | 鉴权 |
|---------|------|--------|------|
| **独立模式** | 独立部署 | 自己的数据库 | 自己的登录态 |
| **嵌入模式** | 作为 app 模块打包进 molding-expert-web | 共享 molding-expert 的数据库 | 共享 molding-expert 的登录态 |

### 1.2 Model 直接复用原则

- mold model 沿用 molding-expert-web 为基础
- **可以由 optima 主动优化**（不是被动接受）
- **优化后必须同步更新 molding-expert-web**（保持双系统一致）
- 不需要 Wrapper/Adapter 层来"妥协"嵌入模式
- 当前 mold model 设计**已经合适**，不需要大改

### 1.3 基础模块不主动移除

- 默认保留一切从 molding-expert 拷贝过来的基础模块
- 包括 project（即使业务上不需要）
- 只有在明确业务需求时才考虑减少/移除

## 二、模型设计哲学

### 2.1 旧模型 vs 新模型的核心差异

| 维度 | 旧 HsMoldingService 模型 | 新 molding-expert 模型 |
|------|----------------------|---------------------|
| 用途 | 测试和输入 | 数据存储 |
| 字段组织 | 平铺（用户视角）| 分层（技术视角）|
| 多射/多色 | ❌ 不支持 | ✅ Mold → N GatingSystem |
| 家族模具 | ❌ 单行 project | ✅ 1 Project → N Mold |
| 一模多腔 | ❌ cavity_num 是 CharField | ✅ Cavity 表 |
| 浇口多样性 | ❌ 字段冗余 | ✅ Gate 表 + gate_shape |
| 关系建模 | ❌ IntegerField 假装 FK | ✅ 严格 ForeignKey |
| 工程化字段 | ❌ | ✅ verbose_name + help_text + 公式 |

**用户原话**：
> "旧模型能够用，但是描述的场景有局限，你可以理解成旧模型打出的产品是明确，且单一的"
> "这样的 mold 只具备实验价值，没有工程价值"

### 2.2 新模型结构（mold.py）

```
Mold（模具）
└── Mold.project → Project（家族模具：1 Project → N Mold）
└── Mold.shot_count → 决定有几个 GatingSystem

GatingSystem（每次注射的工艺上下文）
└── 1 Mold → N GatingSystem（支持多射/多色）
└── GatingSystem.runner_type, hot_runner_*, sprue_bushing_*, estimated_shot_weight...
└── GatingSystem → N Cavity

Cavity（每次注射的产品）
└── GatingSystem → N Cavity（支持一模多腔）
└── Cavity.cavity_count_per_shot, product_name, product_code, 壁厚参数...
└── Cavity → N Gate

Gate（每个产品的浇口）
└── Cavity → N Gate（支持多种浇口形状）
└── Gate.gate_shape, gate_count, 尺寸字段（按形状分类）

CoolingSystem（模具冷却，OneToOne Mold）
EjectionSystem（模具顶出，OneToOne Mold）
```

### 2.3 工艺建模的基本单位

**GatingSystem = "一次注射成型"的工艺单元**（不是冗余）：

> "对于注射成型，实际上我们每次关注的，就是一次注射，即使是多射成型，我们也就是关注那一次的内容"
> "gating其实是作为区分的"

- 单射模具：1 GatingSystem
- 多射模具：N 个独立 GatingSystem（每次独立优化）
- Cavity = 一次注射的产品多样性
- Gate = 一个产品的浇口多样性

### 2.4 字段的算法输入价值

**每个字段都是旧算法的"输入参数"**——字段多不是冗余，是算法输入空间的完整建模。

**用户原话**：
> "我们肯定是要用新模型的，但是我们旧系统的算法，其实是散落在新模型中各个地方字段，最后组装成的结果"

设计原则：
- 字段不能删除（破坏算法依赖）
- 算法应该显式实现（不散落在表单/UI 中）
- 字段命名要规范（便于算法引用）

## 三、双视角设计哲学

### 3.1 存储层 vs 输入层

| 层 | 策略 | 原因 |
|----|------|------|
| **后端 schema** | **保持完整** | 工程价值需要，字段都是算法输入 |
| **前端表单** | **简化输入** | UX 考虑，90% 用户不需要填所有字段 |

### 3.2 输入组织原则

- Mold 字段平铺（用户视角）
- GatingSystem/Cavity/Gate 子表用"卡片 + 标签"显式表达
- 不能照搬旧字段混乱部分
- 不能把新模型分层照搬到表单

### 3.3 旧字段的取舍

**保留**：平铺组织（用户视角）、业务命名、字段集中
**清理**：注释字段、错误类型（cavity_num 应为 IntegerField）、冗余字段

## 四、弹性填写与向下兼容

### 4.1 弹性填写场景矩阵

| 场景 | Mold 填写 | GatingSystem | Cavity | Gate | 等价于旧模型 |
|------|----------|--------------|--------|------|------------|
| **极简** | 必填 | 1 个 | 1 个（count=1）| 1 个（count=1）| ✅ 完全等价 |
| **简单** | 必填 | 1 个 | 1 个（count=N）| 1 个 | 旧模型无法表达 |
| **中等** | 必填 | 1 个 | N 个 | N 个 | 旧模型无法表达 |
| **复杂** | 必填 | N 个 | N 个 | N 个 | 旧模型无法表达 |

### 4.2 向下兼容的本质

**新模型通过"最少填写"兼容旧模型**：
- ✅ 旧 mold 的所有数据可以无损迁移（按"最少字段版本"）
- ✅ 不需要为兼容旧场景而保留旧的字段混乱设计
- ✅ 旧场景的"信息缺失"被新模型自然解决

## 五、前端设计目标与挑战

### 5.1 设计目标（三位一体）

1. **好用**：UX 体验，不让用户面对复杂嵌套
2. **实现历史功能**：向下兼容——历史 mold 的功能都要能做
3. **可扩展**：未来能加字段、加场景

> "我们要做通用产品，就不能像试验品那样设计"

### 5.2 推荐方案：渐进式嵌套 + 层级标签化

```
┌─────────────────────────────────────────┐
│ Mold 基本信息（必填，平铺）               │
│ - 模具编号、模具名称、shot_count         │
├─────────────────────────────────────────┤
│ 🏷️ 注射成型配置                          │
├─────────────────────────────────────────┤
│ ┌─ 注射 1 [GatingSystem #1] ─[展开▾]─┐ │
│ │  流道、热流道、主流道衬套、工艺估算     │ │
│ │  ┌─ 产品 A [Cavity] ─count=4─[展开▾]┐│ │
│ │  │  product_name, 壁厚参数...        ││ │
│ │  │  ┌─ 浇口 [Gate] ─count=2─┐       ││ │
│ │  │  │  gate_shape, 尺寸...   │       ││ │
│ │  │  └────────────────────────┘       ││ │
│ │  └──────────────────────────────────┘│ │
│ └────────────────────────────────────────┘ │
│ [+ 添加注射]                             │
└─────────────────────────────────────────┘
```

### 5.3 关键设计要素

| 要素 | 作用 | 避免 molding-expert 的问题 |
|------|------|--------------------------|
| **层级面包屑**（"注射 1 > 产品 A > 浇口"）| 显式表达嵌套 | ❌ molding-expert 没有清晰标识 |
| **可折叠卡片**（▾ / ▸）| 平铺与嵌套切换 | ❌ 强制全部展开？ |
| **标签化命名**（"注射 N"、"产品 N"）| 让用户知道当前在哪一层 | ❌ 命名不清晰 |
| **添加按钮**（+ 添加注射/产品/浇口）| 支持弹性填写 | ❓ |
| **场景化字段**（按 shot_count 隐藏/显示）| 减少视觉负担 | ❌ |

## 六、Project 表的维护策略

### 6.1 关键澄清

**之前我误以为用户在问"要不要保留 project"——错了**。

**真正的问题**：project 在 molding-optima 中**以什么方式维护/呈现**？

### 6.2 候选维护方式

1. **完全隐藏**：不显示路由/菜单，仅保留 mold.project 外键
2. **只读展示**：显示路由，但只有查看功能
3. **附属化（推荐）**：不显示独立页面，mold 创建时下拉选择
4. **内嵌化**：取消独立模型，字段平铺到 mold（不推荐，违反设计原则）

### 6.3 推荐：方式 C 附属化

- 不显示独立 project 路由/菜单
- mold 创建/编辑时 el-tree-select 选择 project
- mold 详情页显示 project 信息
- mold 列表支持按 project 筛选
- project API 仅 GET（不暴露 POST/PUT/DELETE）

## 七、对话教训沉淀

### 7.1 用户关注点辨析

**当用户问"要不要保留 X"时，先确认真实意图**：
- ❌ 评估业务必要性
- ✅ 探讨交互体验设计（如何呈现/管理）

参考记忆 id：`53bc030a-a3fd-4956-88af-3c3f5d92c1ce`

### 7.2 沟通模式

**避免**：
- ❌ 列抽象"设计选项"让用户挑选
- ❌ 没理解具体场景就展开方案
- ❌ 用技术术语替代业务理解

**正确**：
- ✅ 让用户直接告诉我具体场景
- ✅ 确认理解后再展开
- ✅ 用业务语言而非技术语言

### 7.3 调研方向纠正

**用户明确纠正**：
- ❌ 不要建议补 moldflow/旧版子视图等"缺失功能"——这些可能已被解决或用户认为不重要
- ❌ 不要陷入字段对比/功能补全的陷阱
- ✅ 讨论设计问题，不是解决问题
