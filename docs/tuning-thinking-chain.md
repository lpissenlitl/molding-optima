## 0. 来源：用户的判断（本轮）

> 所以我在想，我们的调机逻辑，是不是一条完整的思维链？
>
> 有缺陷，修缺陷
> 无缺陷，要么结束，要么优化能耗或者周期
>
> 我觉得这些都属于思维链的过程，fuzzy、llm，都属于推理时给的建议，属于经验

⇒ 三个要点：

1. **调机逻辑是**一条**完整思维链**，不是一个「调参动作」。
2. 链的骨架 = **本轮状态 → 该做什么**；`fuzzy` / `llm` / `empirical` 是**推理时给的建议（经验载体）**，
   不是骨架本身。
3. 「调缺陷」与「优化能耗/周期」**同属一条链**，不是两套系统。

---

## 1. 链的形状

```
             ┌─ 有缺陷 ────→ 环节① 修缺陷
本轮状态 ────┤
             └─ 无缺陷 ──┬─→ 环节② 优化能耗 / 周期
                          └─→ 环节③ 结束（无可省项）
```

每环**同构**，四段式：

```
准入判据 → 判据源 → [L1 载体给建议] → L2 裁决 → L3 落地 → L4 校验
              ↑ 环节之间不同         ↑ 环节之间相同（同一个 L2、同一个 L3/L4）
```

- **环节之间不同的只有两样**：**准入判据** + **判据源**。
- **载体**（`fuzzy` / `llm` / `empirical`）是**环节内的推理手段**；一个环节可有多个载体，
  环节内按优先级取 ⇒ 「谁先谁后」只在**环节内**成立，环节之间**不抢话**。

⇒ 「fuzzy 只处理缺陷部分」在这个模型里是**载体属性**，不是限制：
fuzzy 的规则库是**缺陷触发** ⇒ 它天然只能服务环节①。

### 2.1 「合格态报错」的定性（**已闭环**，2026-11-25）

**原状**：合格态 ⇒ 无缺陷 ⇒ fuzzy 零产出 ⇒ `_infer_kernel` fail-fast ⇒ 事务未进。

**在链模型下这不是 bug，是骨架缺失** —— 合格态在链上该落到环节②③，
但它既无准入判据也无出口 ⇒ 掉进「无产出 ⇒ fail-fast」的空洞。

**修法**（**已落地，15.1**）：不是加一个 `if` 特例分支，而是**把环节②的出口建出来** ——
**场景自带候选**（`candidate_params`）+ **口径解算目标值**（`step_down` = 递减步进）
⇒ 合格态有了真实产出 ⇒ **不新建引擎、不新判据源**，仍走同一条 L1–L4 分层。

⇒ 与本文的判断一致：**环节②不靠新载体，靠调机策略**（fuzzy / llm 仍是经验载体，
只是**合格态没有缺陷经验可依** ⇒ 候选与目标值改由**场景 + 口径**给出）。

### 2.2 载体语义错位的连带好处

环节①准入 = 「有缺陷」、环节②准入 = 「无缺陷且合格」⇒ **天然互斥、天然有序**
⇒ `qualified-tuning-boundary.md` §6 的 **R6「经济性源与缺陷源并存/互斥」自动消解**
（载体视角下要拍「优先级争抢」，环节视角下不存在）。

## 3. 与既有「阶段」概念的关系（**待议**）

代码里已有 `STAGE_ORDER = ('filling', 'shrinking', 'appearance')` —— 由**缺陷码**推导，
用于**环节①内部**的分段推进（`derive_stage_progress`）。

| 概念 | 推导来源 | 作用 | 与「环节」的关系 |
|---|---|---|---|
| **阶段**（filling / shrinking / appearance） | 缺陷码 | 环节①内推进到哪一步 | 环节的**内部**结构 |
| **环节**（修缺陷 / 优化能耗 / 结束） | 有无缺陷 + 合格与否 | 换判据源 | 顶层 |

⇒ **待议 A**：两层**分开**（推导来源不同，混在一层会互相干扰）还是**统一成一层**。

### 4.2 E 环缺口的证据链（**为什么说它最实**）

1. `ScenarioStrategy.priority_table` 默认**空表**（`decide_adjustment.py` L343）；
2. **8 条场景策略无一填表**（`decide_adjustment.py` 里 `priority_table` **零命中**）；
3. `resolve_priority` 的排序键 = `(场景优先集次序, table.priority_of(name), 候选原始下标)`
   （L486-493）⇒ 空表时 `priority_of` 恒返回 `default_priority=1000`
   ⇒ **第二排序键完全失效**；
4. ⇒ 实际次序 = **场景优先集内次序 → L1（fuzzy 规则库）产出顺序**；
5. 而场景的 `max_items=1`（U-01「一轮只改一个量」）⇒
   **「这一轮动哪个旋钮」实际由规则库的命中顺序决定**；
6. `PriorityTable.group_of`（业务分组）**零消费方** ⇒ 组级分组的**位子留好了、从没用过**。

**而业务答案其实已经有了** —— 规则原料 §7.2「各缺陷的动作顺序（一轮只动一个 ⇒ 顺序即优先级）」：

| 缺陷 | 顺序 |
|---|---|
| 短射 | 排除泄漏 → 胶量端 → （MEL 到头）转位 → 充填速度 → 压力受限排查 |
| 缩水 | 充填量 → 二段压力 → 二段时间 → 模温 → 熔温 → 充填速度 |
| 飞边 | 二段压力 → 胶量端 → 切换过冲 → 熔温 → 锁模力/模具 |
| 烧焦 | 清模/排气 → 熔温 → 背压 → 松退 → 充填速度 |
| 周期 | 熔温 → 模温 → 冷却时间 → 充填速度 → 各段时间冗余 |

⇒ **数据源现成**（§7.2）、**表达位现成**（`PriorityTable` 的 `group` / `priority`，
且 `ScenarioStrategy.priority_table` 就是「本场景的字段级优先级表」）、
**只差消费一环**（`resolve_priority` 不读组间次序）。

⇒ 对应未决项：`docs/open-questions.md` **Q1**（是否要独立的「参数组级」配置层）、
**Q4**（L2 优先级顺序 —— 「现状只做『场景优先集 + 名额』，**组级次序未做**」）。

### 4.3 G 环缺口（次实）

`resolve_scheme` 的第 1 步（L797-801）：保留项的**非派生量**目标值**原样**取自 L1 建议
⇒ L1 给多少就是多少，L2 不参与「改成多少」。
（`met_end_pos` 是唯一例外 —— 走 `fill_ratio` 口径，§12 已定型。）
